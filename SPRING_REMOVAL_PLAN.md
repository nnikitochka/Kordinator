# План перехода на самостоятельный музыкальный бэкенд

**Первый этап — удалить встроенный JSP-сайт из текущего приложения.** Начинаем с него сразу. Иконки старого сайта сохраняем в репозитории для дальнейшего использования. После этого собираем собственный музыкальный API на Kotlin и standalone Ktor для Youamp Desktop.

В первую версию входят локальные учётные записи и сессии, управление музыкальными папками и сканированием, каталог и поиск, обложки, аудиопоток и плейлисты. Совместимость с Subsonic/OpenSubsonic и прежними HTTP-контрактами Airsonic исключена из требований. Формат хранения существующих пользовательских данных и возможность их импорта рассматриваем отдельно. Все работы проверяем на временной БД и тестовой медиатеке.

[Журнал прежней миграции](docs/migration/SPRING_REMOVAL_HISTORY.md) содержит выполненные срезы и результаты тестов. Его можно использовать при выборе уже готовых компонентов.

## 1. Удалить JSP и сохранить иконки

### 1.1. Сохранить графические ресурсы

- Перенести весь `airsonic-main/src/main/webapp/icons/` и корневой `favicon.ico` в `contrib/assets/legacy-web-icons/`. Сохранить вложенные пути и связанные файлы с лицензиями и атрибуцией. По текущему индексу Git в `icons/` 648 файлов.
- В `style/` и `script/` отдельно собрать иконки управления плеером, спрайты и остальные графические иконки, включая ресурсы сторонних библиотек с их атрибуцией. Сохранить их в том же каталоге с исходными относительными путями. Сверить список перенесённых файлов и содержимое с деревом Git до удаления сайта.
- Проверить ссылки из сервисов, конфигурации и тестов на файлы из `webapp`. Ресурсы, которые читает работающий бэкенд, перенести в classpath и обновить их потребителей. Например, запасная обложка уже лежит в `src/main/resources/org/airsonic/player/controller/default_cover.jpg`. Иконки для будущего клиента остаются в `contrib/assets`.

### 1.2. Удалить страницы и их маршруты

- В `AirsonicKtorServlet` удалить переходы в `/WEB-INF/jsp`, настройку контекста для JSP и подготовку моделей страниц. В `KtorConfiguration` снять регистрацию экранов, их псевдонимов и эндпоинтов данных, обслуживающих только эти экраны. Сюда относятся вход, настройки, фреймы медиатеки, страница очереди, HTML-восстановление пароля и публичный HTML-плеер из `externalPlayer.jsp`.
- Убрать главную страницу, раздачу `/script/*`, `/style/*`, `/icons/*` и браузерные файлы из `KtorInfrastructureRoutes` и servlet mappings. Проверить welcome-файлы, legacy fallback, перенаправления, правила безопасности и ответы на ошибки. Для удалённых страниц целевой ответ — `404` без HTML-перенаправления или JSP dispatch.
- Разобрать смешанные обработчики по маршрутам. Например, у `PublicShareController` есть HTML-страница и отдельный подписанный маршрут данных. Удалить страницу сейчас, а вызовы общего кода для потоков, прав и медиа проверять отдельно. Исторические маршруты остаются только на время работы старого запуска и целиком уходят при переключении на новый.
- Удалить страницы, TLD, сайт и его клиентский JS/CSS, оставшиеся в `src/main/webapp`. Убрать осиротевшие классы моделей, JSP taglib и theme wiring. Бэкенд-локализацию или настройки удалять после проверки их потребителей.
- В `GlobalSecurityConfig` убрать form login, remember-me и перенаправления на удалённые страницы. Сохранить проверки подлинности и прав для маршрутов, которые ещё работают в переходном приложении. CSRF и связанные адаптеры убрать после проверки, что ни один оставшийся защищённый маршрут не принимает cookie как подтверждение входа.

### 1.3. Почистить сборку и доказать результат

- Убрать Jasper, JSP API, JSTL, taglibs и JSP ruleset PMD из `airsonic-main/pom.xml`. Удалить JSP-настройки сканирования TLD из `TomcatApplication`. Текущую упаковку и Ktor servlet adapter можно использовать на этом этапе для запуска API без сайта. Переход на самостоятельный процесс — следующий этап.
- Удалить проверки HTML и JS, которые обслуживали только сайт. В смешанных тестах вроде `PublicShareIntegrationTest` удалить ожидания страницы и сохранить проверки действующих HTTP-операций. Запустить целевые регрессии сканирования, прав доступа, стриминга, HLS, обложек и health для оставшихся маршрутов.
- Собрать артефакт и запустить его на временной БД. Проверить, что он стартует без Jasper, JSP/TLD и сайт отсутствуют в артефакте, корень и выбранные удалённые страницы возвращают `404`, текущие защищённые API по-прежнему отклоняют запросы без подходящих учётных данных, а health и разрешённый поток работают. Повторно сверить иконки и их атрибуцию с исходным деревом.

**Этап завершён**, когда удалён весь рабочий JSP-сайт вместе с привязками и зависимостями, иконки сохранены, серверный артефакт запускается и HTTP-проверки проходят. Тестирование в Firefox не требуется.

## 2. Запустить standalone Ktor и сделать вход

1. Добавить Kotlin-точку входа и Ktor application module. Переиспользовать `RuntimeConfiguration`, `RuntimeCompositionRoot` и `LifecycleRegistry` там, где они подходят. Подключить явный жизненный цикл конфигурации, JDBC-пула и Liquibase, затем JSON-ошибки и health. Блокирующий JDBC и файловые операции выполнять на подходящем ограниченном исполнителе.
2. Подготовить модель локального пользователя и сессии. У пользователя хранить логин, индивидуально посоленный Argon2id-хеш пароля и состояние учётной записи. Первого администратора создавать командой с защищённым вводом пароля. Ограничивать частоту попыток входа и возвращать одинаковую ошибку для неизвестного пользователя и неверного пароля. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
3. Реализовать `POST /api/v1/auth/login`, `GET /api/v1/me` и `POST /api/v1/auth/logout`. При успешном входе сервер выдаёт токен из 32 случайных байтов (`SecureRandom)). В БД хранится отдельная запись о сессии с хешем токена SHA-256, ID пользователя и сроком действия. Клиент дальше присылает токен в `Authorization: Bearer <token>`, сервер вычисляет его хеш и ищет действующую сессию. Клиент работает по HTTPS, пароль и токен исключаются из логов. [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#server-side-session-token-storage)
4. Настроить аутентификацию Ktor с явным списком публичных маршрутов. При выходе отзывается текущая сессия, при смене пароля — все сессии пользователя. Отключение учётной записи сразу лишает доступа. Проверки ролей и прав на ресурсы опираются на актуальное состояние учётной записи. Недействительная сессия получает `401`, отсутствие прав на видимый ресурс — `403`.

**Этап завершён**, когда самостоятельный процесс стартует на пустой БД, а HTTP-тесты проверяют создание администратора, вход, `/me`, перезапуск с действующей сессией, отзыв, истечение срока, смену пароля и отключение пользователя. Cookie, HTTP Basic и query-параметры не должны подтверждать вход в новом API. Сроки проверяем с управляемыми часами. Отдельно проверяем корректную остановку процесса и освобождение ресурсов.

## 3. Подключить каталог, поиск и воспроизведение

- Подключить музыкальные папки, метаданные, сканер, индекс и необходимые DAO через явные зависимости. По мере подключения заменять оставшиеся Spring-привязки этих компонентов. Проверить запуск и остановку сканера и фоновых задач.
- Спроектировать собственные JSON-модели и маршруты для исполнителей, альбомов, треков и поиска. Описать идентификаторы, пагинацию, сортировку и ошибки в OpenAPI. Ограничивать выборки библиотеками, доступными пользователю.
- Подключить обложки и прямой аудиопоток с корректными MIME, длиной и byte ranges. Сервер проверяет доступ к треку и обложке при запросе по ID. Транскодирование подключать по требованиям Youamp Desktop после проверки прямого воспроизведения.

**Этап завершён**, когда после сканирования временной папки клиент находит альбом и воспроизводит его трек. Проверки покрывают повторное сканирование, поиск и пагинацию, обложку, полную и частичную выдачу аудио, перемотку и отказ в доступе к чужому треку или обложке.

## 4. Подключить управление и проверить Youamp Desktop

- Добавить операции с плейлистами и их порядком треков, управление пользователями и правами, создание и настройку музыкальных папок, запуск и статус сканирования. Согласовать форматы и ошибки с клиентом по OpenAPI.
- Проверить HTTP-сценарии с администратором и двумя обычными пользователями. Покрыть создание и изменение плейлиста, сохранение порядка, отказ для чужого плейлиста, изменение прав на папку, запуск сканирования и запрет административных операций обычному пользователю.

**Этап завершён**, когда Youamp Desktop проходит основной сценарий от входа до воспроизведения и сохранения плейлиста, а серверные тесты подтверждают разграничение доступа.

## 5. Переключить запуск и удалить Spring и старое API

- Сделать standalone Ktor основным исполняемым артефактом. Убрать прежний bootstrap, `AirsonicKtorServlet`, Servlet/Tomcat, Spring Security, Spring web/DI и старые HTTP bindings, включая `/rest`, `/ext` и `.view`. Удалить Subsonic DTO и модуль `subsonic-rest-api` после проверки зависимостей и переноса нужной логики из старых обработчиков.
- Убрать оставшиеся Spring-привязки из сервисов, DAO, тестов и сборки. Проверить Liquibase на чистой базе и границы перенесённых транзакций. Удалить Boot parent/BOM и плагины после явного закрепления нужных версий. Удалить WAR-конфигурацию, переключить Docker и workflows на новый артефакт, обновить команды запуска. Перенести полезные медиафикстуры из старых интеграционных тестов.
- Запустить тесты reactor, собрать артефакт и проверить запуск, миграции, health, вход, каталог, поток и остановку на временных данных. Проверить исходники, effective POM, деревья compile/runtime/test-зависимостей и содержимое релизного артефакта на Spring, Servlet и JSP. Проверить, что прежние маршруты отсутствуют в новом процессе и все поддерживаемые сценарии идут через `/api/v1`.

**План завершён**, когда релизная сборка и Docker запускают один standalone Ktor-сервер с собственным API, тесты нового контракта проходят, исходники и зависимости Spring/Servlet/JSP удалены, а иконки старого сайта доступны в репозитории.

Каждый срез коммитим вместе с проверкой затронутого поведения. Сборка и запуск текущего этапа должны проходить к концу каждого среза. Ошибки окружения и непроведённые проверки фиксируем явно.
