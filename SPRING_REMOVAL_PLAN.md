# План перехода Kordinator на самостоятельный музыкальный бэкенд

## Цель и границы

Kordinator запускается из основного Maven-модуля `airsonic-main` как один сервер Ktor Netty. Клиент работает с собственным HTTP API `/api/v1`. Развитие продолжается в существующем приложении с его сканером, индексом, сервисами и DAO. Новые классы пишем на Kotlin, кроме случаев, когда это заметно усложняет перенос.

Первая версия включает локальные учётные записи и сессии, права на музыкальные папки, управление библиотеками и сканированием, исполнителей, альбомы, треки, поиск, обложки, прямое аудио, плейлисты и избранные треки. Встроенный JSP-сайт уже удалён, иконки сохранены в `contrib/assets/legacy-web-icons/`. Старые URL, XML/JSONP-конверты, Subsonic/OpenSubsonic, cookie и логин с паролем в каждом запросе не входят в контракт нового клиента. `getLicense` удалён из требований.

Перед удалением старого участка кода прослеживаем вызовы до сервиса и хранилища. Прикладное поведение сохраняем в действующем маршруте или сервисе. Если возможность выходит за рамки первой версии, фиксируем её судьбу отдельно от судьбы старого протокола. Удаление старых данных или ещё не перенесённой возможности требует отдельного решения.

[История удаления Spring](docs/migration/SPRING_REMOVAL_HISTORY.md) содержит прежние этапы и коммиты. [Матрица поведения](docs/migration/BEHAVIOR_PRESERVATION_MATRIX.md) помогает разбирать старые обработчики. Актуальный порядок работ и критерии закрытия приведены ниже.

## 0. Зафиксировать карту текущего запуска

**Статус:** карта реально зарегистрированных `/api/v1` маршрутов и их пробелов записана в [матрице поведения](docs/migration/BEHAVIOR_PRESERVATION_MATRIX.md). Подтверждено, что `main` запускает `standaloneModule`; `controller/rest/**` и отдельно тестируемые `Kordinator*Routes` из production-кода не регистрируются. Сверка каждой операции с нужным старым поведением и приёмка одного упакованного запуска остаются открыты.

1. Начать с `main` и `standaloneModule` в `airsonic-main/src/main/java/org/airsonic/player/ktor/KtorApplication.kt`. Для каждого реально подключённого маршрута записать HTTP-метод, путь, способ получения пользователя, сервис, источник данных и тест.
2. Сверить список с `ktor/Kordinator*Routes.kt` и прежними `controller/rest/**`. Для каждой операции в матрице указать статус: подключена в JAR, реализована отдельно, сохранилась только в старом коде или снята по решению проекта. Если одноимённые обработчики отличаются по правам, результату или идентификаторам, записать разницу.
3. Привязать тесты к этой карте. `KtorStandalone*Test` проверяет текущую регистрацию в тестовом сервере. Проверки из `Kordinator*RoutesTest` переносим на действующую регистрацию по мере подключения соответствующего кода. Отдельно сохраняем проверки сервисов и DAO.
4. Зафиксировать результат подключения основных сценариев к артефакту. Использовать временный home, тестовую медиатеку, локальный порт и текущие команды из README и `.github/workflows/pr_ci.yml`. Проверить health, ответы на удалённые пути и чистую остановку. Сохранить команду, коммит и фактический результат в журнале.

**Готово, когда** по каждой операции видно, исполняется ли она в JAR, какие данные меняет и какой проверкой это подтверждено. По активному и архивному дереву ведём отдельный учёт.

## 3. Подключить права, каталог, сканирование и воспроизведение

**Зачем:** пользователь должен пройти весь музыкальный сценарий в одном процессе, с теми же правами при выдаче списков, деталей, обложек и потока.

**Статус каталога/поиска:** `GET /tracks`, `/search`, `/albums` и `/artists` теперь проверены на двух реально просканированных библиотеках с одинаковыми названиями и метаданными. Composite ID сохраняет различие библиотек, порядок и границы страниц повторяются, `total` не зависит от текущей страницы, а обычный пользователь видит только свой total. Для альбомов и исполнителей total включён в ответ; пустая выдача и некорректные параметры покрыты отдельными assertions в интеграционных тестах.

**Статус потока и artwork:** stream проверен на `200`, `206`, точные байты/`Content-Range`, `416`, `Accept-Ranges`, `ETag`, `Last-Modified`, `304` по обоим условным заголовкам, удалённый файл и отсутствие доступа. Artwork проверен на локальное изображение и прежний fallback `default_cover.jpg`, SHA-256 `ETag`, `304`, `private, max-age=300`, отсутствие ложного `Last-Modified`, отсутствие трека и границы доступа.

**Статус сквозной проверки:** `KtorStandaloneRealScanIsolationTest` проходит через реальную регистрацию маршрутов и `MediaScannerService`: создание библиотек, вход и назначения, сканирование, каталог/поиск, детали, обложка, полный и частичный поток. Проверки второго пользователя подтверждают запрет деталей, обложки, потока и библиотечного каталога без назначения.

1. **Права на библиотеки.** В `standaloneModule`, `KtorCoreMediaCatalogService` и сервисах избранного/плейлистов связь хранится в `local_user_library` по ID локального пользователя и core `music_folder`. Активные `GET/PUT /admin/users/{id}/libraries` читают и меняют назначения; администратор видит все папки, обычный пользователь — только выданные. Bearer-аутентификация читает актуальный набор прав на каждый запрос. Список и total, поиск, детали по ID, поток, обложки, избранное и содержимое плейлистов получают тот же scope. Проверены отказ без прав, выдача и отзыв доступа без перевыпуска токена, чтение во время выданного доступа, 404 для чужого ID/потока и миграция БД с сохранением пользователя и сессии. Реальный сканер теперь проверен вместе с двумя обычными пользователями, назначенными на разные библиотеки: каждый видит и слушает только свою. Осталась проверка обновления копии рабочей БД.
2. **Сканирование.** Есть два интеграционных сценария через зарегистрированные маршруты: один с изолированными mock core-сервисами проверяет создание папки через `POST /admin/libraries` и поток; второй использует настоящий `MediaScannerService` и MP3 fixture, сканирует две библиотеки и проверяет выдачу треков/байтов двум пользователям с разными правами. Проверены повторное сканирование без дублей и со стабильным ID, изменение размера существующего файла с сохранением ID, удаление файла с исчезновением трека из каталога, конкурентный enqueue (побеждает одно задание, второе получает `409`), ошибка недоступного корня и восстановление оставленного `RUNNING` задания при создании сервиса после перезапуска (помечается `FAILED`). Rename на диске создаёт новую запись с новым ID; прежний ID больше недоступен через каталог. API отмены сканирования сейчас нет, поэтому отмена не является поддержанным сценарием. Остаётся проверить восстановление на копии рабочей БД. Перенос/переименование не связывает автоматически прежние ссылки избранного и плейлистов с новым ID.
3. **Каталог и поиск.** Сверить текущие `/artists`, `/albums`, `/tracks`, запросы по ID и `/search` с поведением `MediaFileService`, DAO и индекса. Зафиксировать смысл ID исполнителя и альбома, различение одинаковых имён в разных библиотеках, порядок при равных значениях, total, лимиты, формат времени и метаданные. Подключить существующий поиск там, где требуется его семантика. Приёмка: разные теги, одинаковые названия, пустая выдача, ошибка параметров, воспроизводимая сортировка и страницы с теми же границами доступа.
4. **Аудио и обложки.** Сверить активные `/tracks/{id}/stream` и `/tracks/{id}/artwork` с существующими сервисами чтения, обложек и условных запросов. Проверять путь внутри разрешённой папки до чтения. Описать полный и частичный ответы, MIME, длину, условные заголовки и ошибки. Приёмка: `200` с верным содержимым, `206` с правильными байтами и `Content-Range`, `416` для невыполнимого диапазона, перемотка, отсутствие файла и запрещённый доступ. Для обложки проверить запасное изображение, кеширование и доступ.
5. **Сквозная проверка.** На временной БД зарегистрировать пользователя, добавить папку с небольшим аудиофайлом и обложкой, запустить сканирование и дождаться окончания, найти трек через поиск, прочитать альбом, получить обложку, проиграть трек и сместиться по диапазону. Повторить запросы от второго пользователя без доступа. Если API не предоставляет настройку прав для этой проверки, связать её с пунктом 4.1.

**Готово, когда** один набор HTTP-проверок проходит через реальную регистрацию маршрутов и реальные сервисы. Положительные тесты на отдельных обработчиках сохраняют ценность для отладки и дополняют сквозную проверку.

## 4. Закрыть управление и клиентский контракт первой версии

| Шаг | Где и что сделать | Как принять |
|---|---|---|
| 4.1. Администрирование | `standaloneModule` обслуживает список/создание пользователей, смену имени, роли и включённости, удаление аккаунта, назначения библиотек; каталог библиотек, создание, переименование, запуск и статус сканирования. Удаление пользователя каскадно удаляет его сессии, плейлисты и их треки, избранное и назначения библиотек; нельзя удалить себя или последнего включённого администратора. Смена роли отзывает активные сессии. `KtorStandaloneAuthTest` покрывает обычный и админский доступ, уникальность, действующие/отозванные сессии, каскад и защиту последнего администратора. `KtorStandaloneLibraryTest` проверяет создание, список и переименование библиотеки. | Шаг закрыт для существующего API. `KtorStandaloneLibraryTest` проверяет, что переименование меняет только имя и сохраняет ID, путь, физические файлы и назначения библиотек. `KtorFileDatabaseCopyTest` повторно сканирует переименованную библиотеку и проверяет сохранение доступа, ID трека, плейлиста и избранного после копирования и повторного открытия обеих БД. Ktor-маршрутов смены пути и удаления библиотеки нет; их добавление — отдельное изменение контракта. Старый `MediaFolderService.deleteMusicFolder` сохраняет физические файлы, но удаляет индексированные записи `media_file` и переводит папку в удалённое состояние. |
| 4.2. Плейлисты | В `StandalonePlaylistService`, существующем `PlaylistService`, DAO и маршрутах плейлистов определить владельца записей и поведение при пропавшем треке. Подключить единый путь CRUD. Сохранять порядок и согласованно обрабатывать повторяющиеся треки и треки из недоступных папок. | Создание, изменение порядка, чтение и удаление после перезапуска. Чужой пользователь не может читать, менять и удалять закрытый плейлист. Ошибка в середине обновления сохраняет целостность прежней записи. |
| 4.3. Избранное | `StandaloneFavoriteService` и маршруты `/favorites/tracks`, `/favorites/albums`, `/favorites/artists` обслуживают списки; `PUT/DELETE` по track ID и composite catalog ID добавляют и удаляют избранное. Для альбомов и исполнителей ID состоит из library ID и точного имени, чтобы одинаковые названия в папках не сливались. Чтение повторно сверяет записи с текущим каталогом и правами доступа. `KtorStandalonePlaylistTest` покрывает базовые операции и приватность; `KtorStandaloneAuthTest` проверяет каскад при удалении аккаунта. | `KtorStandaloneRealScanIsolationTest` проверяет добавление избранного альбома и исполнителя через HTTP, сохранение после реального повторного scan, сокрытие при отзыве доступа к библиотеке и возврат после восстановления доступа. |
| 4.4. OpenAPI | Добавить версионированный контракт, например `docs/api/openapi.yaml`, и сверить его с зарегистрированным `/api/v1`. Для каждой операции записать метод, путь, права, параметры, тип ответа и ошибки. Зафиксировать правила пагинации, идентификаторы, кодировку, типы аудио и Range. | Контракт описывает реально подключённые маршруты и проверяется в CI. Примеры совпадают с ответами собранного приложения. |
| 4.5. Desktop-приёмка | Запустить существующий desktop-клиент против тестового сервера. Пройти вход, листинг, поиск, обложку, воспроизведение, перемотку, создание плейлиста и повторный вход. Зафиксировать версию клиента и сервера. Если сборка клиента недоступна, проверить HTTP-сценарий CLI и оставить отдельный пункт desktop-приёмки открытым. | Клиент прошёл сценарий целиком. Серверная проверка отдельно прошла с двумя наборами прав. Firefox для этой задачи не требуется. |

## 5. Перенести нужное поведение и разобрать старое API

**Зачем:** убрать лишние handlers, фабрики и DTO без потери логики. Этап можно выполнять по завершённым группам параллельно с этапами 3 и 4. Удаление общего модуля идёт после разбора всех его потребителей.

| Группа | Где искать | Что решить и проверить перед удалением |
|---|---|---|
| Очередь, Now Playing, Jukebox | `controller/rest/{playqueue,livequeue,nowplaying,jukebox}`, `PlayQueueService`, статусы, плееры | В standalone API есть отдельная сохраняемая очередь пользователя (`GET/PUT/DELETE /api/v1/me/play-queue`) с порядком, текущим треком и позицией; она возвращает только доступные пользователю треки и восстанавливается по bearer-аккаунту. Это пока не live player: repeat, shuffle, переходы треков, Now Playing и управление аудиодекодером остаются отдельными решениями. Для следующего среза проверить восстановление между сессиями, границы доступа и сохранность очереди при сканировании. |
| Транскод, HLS, видео, субтитры, текст песен | Старые stream/HLS/video/captions/lyrics обработчики и соответствующие сервисы | Сопоставить прямой аудиопоток с остальными режимами. Для каждой сохраняемой операции записать целевой API и проверки формата, прав и ошибок. |
| Шаринг и загрузки | Shares, public share, download, upload и их сервисы | Сохранить правила владения, срок и отзыв ссылки при переносе шаринга. Для загрузок и скачивания проверить границы разрешённой папки, авторизацию, лимиты, прерывание передачи и очистку временных файлов. |
| Избранное альбомов и исполнителей, закладки, рейтинг, теги, рекомендации | Starred, bookmarks, rating, tags, genre/top/random/similar, scrobble | Зафиксировать операции чтения и записи, источник данных и сценарий переноса. Проверить права и сохранение пользовательских изменений после сканирования и перезапуска. |
| Дополнительное администрирование | Старые admin/settings/statistics controllers, DLNA, аватары, LDAP, SMTP, восстановление пароля, backup/import | Для каждой функции выбрать API, CLI или настройку запуска с учётом действующих потребителей. Для сохранённых функций проверить применение изменений, рестарт, полномочия и работу с секретами. |

Для каждой строки работать отдельными срезами:

1. Записать старый обработчик, слой логики, хранилище, цель и решение по объёму релиза в матрицу поведения. Если статус возможности неизвестен, оставить открытой и продолжить независимые срезы.
2. Для переносимой операции подключить существующий сервис или выделить из контроллера его прикладную логику. Пройти через реальную регистрацию. Сверить успешный ответ, ошибки, данные и права.
3. Найти все вызовы удаляемого обработчика, в том числе Java ↔ Kotlin, фабрики `RuntimeCompositionRoot`, тесты, Liquibase и ресурсы. Удалить старую обвязку вместе с зависевшей только от неё сборкой. Проверить, что целевой маршрут работает после удаления.
4. После последней группы выполнить `rg 'org\.subsonic\.restapi|JAXBWriter|subsonic-rest-api'` по исходникам и POM. Заменить оставшиеся общие типы в активном коде. Удалить JAXB/MOXy, схему и модуль из reactor и Docker-профиля после проверки других потребителей. Исторические форматы импорта данных проверяются отдельно от HTTP API.

**Готово, когда** у всех прежних операций записана судьба, сохранённые функции проверены, старые HTTP-привязки и ненужные фабрики удалены, Maven reactor собирается без `subsonic-rest-api`.

## 6. Выпустить и проверить один артефакт

1. В README, `install/docker/`, `contrib/kordinator.service` и `.github/workflows/{pr_ci,edge,stable}.yml` сверить имена артефакта, команду запуска, порты, том данных, параметры БД и создание первого администратора. Документировать путь обновления с резервной копии. Отдельно проверить вариант пустого home.
2. Запустить полную проверку reactor под JDK 25. Нынешний Checkstyle спотыкается на Java `switch` в `PlayQueue.java`. Закрыть этот блокер совместимой настройкой инструмента отдельным срезом. Если какой-то анализатор временно пропущен, явно зафиксировать проверку, которая из-за этого осталась открытой. Текущий выборочный CI не заменяет полный прогон.
3. Проверить effective POM каждого активного профиля, деревья compile/runtime/test и сам JAR. Поиск по JAR должен исключать Spring, Servlet, Jasper, Tomcat и JSP в обычных и multi-release путях. Maven-исключение Chameleon остаётся обоснованной защитой от транзитивного Spring.
4. Запустить один и тот же JAR штатной Java-командой и из Docker с временными томами. Проверить health, старт с пустой и обновлённой БД, вход, каталог, обложку, HTTP Range, права и остановку. Проверить, что прежние маршруты получают `404`. Перезапустить на том же томе и убедиться, что данные доступны и миграции повторно не меняют состояние.
5. Сохранить SHA коммита, команды, версии JDK, БД и клиента, результаты и ограничения. Обновлять статус плана в коммите, который закрывает критерий. Релиз считается готовым после закрытия всех критериев этапов 1–6 и записи решений по функциям из этапа 5.

## Как выполнять каждый рабочий срез

### Очередность и ориентиры по времени

Время ниже относится к активной работе одного разработчика. Это оценки для планирования. Длительность обновления существующих БД, переноса дополнительных функций и исправления обнаруженных дефектов уточняется после аудита.

| Очередь | Шаги и зависимость | Ориентир | Результат, после которого идём дальше |
|---|---|---|---|
| А | 0 и начальная проверка 1 | 2–4 часа | Карта зарегистрированных маршрутов и команда для воспроизведения текущего запуска. |
| Б | 2 после карты маршрутов | 1–2 рабочих дня | Проверенный запуск с настройками из файла, владение данными, остановка и жизненный цикл сессии. Сложный перенос данных оценивается по выбранной схеме. |
| В | 3.1 и минимальная часть 4.1 для назначения прав, затем 3.2–3.5 | 2–4 рабочих дня | Первый сценарий от сканирования до звука с положительной и отрицательной проверкой доступа. |
| Г | Остаток 4 после первого сквозного сценария | 1–3 рабочих дня, плюс доступность desktop-клиента | Администрирование, плейлисты, избранное и согласованный контракт первой версии. |
| Д | 5 по готовности отдельных групп | Первые 2–4 часа на оценку всех групп | Каждая группа получает собственную оценку и критерий закрытия. Общий DTO-модуль удаляется после последней группы. |
| Е | 6 и заключительная проверка 1 после остальных этапов | 1–2 рабочих дня на первый полный прогон | Подтверждённый запуск одного артефакта, журнал проверок и решение по всем открытым пунктам. |

### Порядок работы внутри среза

Работать по одной связанной группе маршрутов или одной подсистеме. Номер следующего шага берётся из первой открытой зависимости, которая мешает сквозному сценарию. Указанные интервалы — ориентир на один небольшой срез, без времени на неизвестные дефекты и ожидание клиента.

| От начала среза | Действие и результат |
|---|---|
| 00:00–00:15 | Сверить `git status`, фактическую регистрацию маршрута и его вызовы. Назвать ожидаемый результат и файлы, которые могут измениться. |
| 00:15–00:30 | Найти ближайшую существующую проверку. Для дефекта зафиксировать ожидаемый и текущий результат. Для переноса описать положительный сценарий, отказ и состояние данных после операции. |
| 00:30–01:30 | Сделать одно рабочее изменение в основном модуле. Подключить через действующую точку входа. Если задача распадается на несколько систем, завершить первую проверяемую часть и отметить зависимости следующих. |
| 01:30–02:00 | Прогнать целевые проверки. Для HTTP пройти маршрут через активную регистрацию. Для БД проверить чистый старт и, если меняется схема или путь хранения, обновление копии существующих данных. |
| 02:00–02:15 | Просмотреть diff, записать результат и сделать локальный коммит только по своему срезу. Сохранить незакоммиченные изменения пользователя. |

Для сквозного запуска опрашивать готовность раз в секунду с ограниченным ожиданием, например до 60 секунд на локальной машине. Сканирование ждать по статусу с отдельным таймаутом и фиксировать последний статус при ошибке. Точные сроки реализации оценивать после инвентаризации и первых проверок каждого этапа. Измерять прогресс закрытыми критериями, а не количеством коммитов или файлов.

**Следующий срез** — пункт 4.4: зафиксировать реально зарегистрированный `/api/v1` контракт OpenAPI и проверять его на соответствие Ktor route registration. Проверка копии БД подтверждает сохранение избранного трека и плейлиста при повторном сканировании переименованной библиотеки; `KtorStandaloneRealScanIsolationTest` подтверждает сохранность избранных альбомов и исполнителей, а также их видимость при изменении доступа. Ktor-маршруты смены пути и удаления библиотеки не входят в текущий API. Сквозной путь от входа до range-stream и отрицательные проверки второго пользователя закрыты в `KtorStandaloneRealScanIsolationTest`.
