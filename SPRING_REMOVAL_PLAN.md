# План самостоятельного музыкального бэкенда на Ktor

## Цель

Форк Airsonic становится самостоятельным музыкальным сервером с собственным HTTP API на Kotlin и standalone Ktor. Первый клиент — Youamp Desktop. Бэкенд отвечает за каталог, поиск, выдачу медиа и обложек, плейлисты и управление библиотекой.

Встроенный JSP-сайт, целевой WAR, обратная совместимость с Subsonic/OpenSubsonic и старыми HTTP-контрактами Airsonic исключены из плана. Тесты совместимости прежнего API и UI уходят вместе с соответствующим кодом. [Прежний план и журнал выполненных срезов](docs/migration/SPRING_REMOVAL_HISTORY.md) остаются справочником по существующим компонентам и тестам.

Новый код пишем на Kotlin. Композиционный корень, сканер, индекс, работу с медиа, DAO и тесты предметной логики переиспользуем по мере подключения к новому runtime. Первый запуск проверяем на пустой БД и временной медиатеке. Возможный импорт существующего каталога и пользовательских данных рассматриваем отдельно от совместимости протокола.

## Вход и права доступа

- Клиент один раз за сессию отправляет логин и пароль в JSON на `POST /api/v1/auth/login` по HTTPS. Сервер проверяет пароль и выдаёт сессионный токен со сроком действия. Для последующих запросов клиент передаёт `Authorization: Bearer <token>`. [RFC 6750, раздел 2.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1)
- Для первой версии выбираем непрозрачный токен из 32 случайных байтов, сгенерированных сервером через `SecureRandom`. В БД храним SHA-256 токена, идентификатор пользователя и срок действия. `POST /api/v1/auth/logout` отзывает текущую сессию. Смена пароля отзывает сессии пользователя, а отключение учётной записи сразу лишает доступа. Клиент передаёт сессионный токен только в заголовке. Пароли и токены исключаем из логов.
- Пароли локальных учётных записей храним как Argon2id-хеши с индивидуальной солью. Первый администратор создаётся явной командой и задаёт пароль через защищённый ввод. На входе ограничиваем частоту попыток и возвращаем одинаковую ошибку для неверного пароля и неизвестного пользователя. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- Ktor проверяет сессию и устанавливает личность пользователя. Сервер проверяет актуальные роли и доступ к конкретной библиотеке или плейлисту при каждом обращении к ресурсу. Ошибка аутентификации возвращает `401`, отсутствие прав на видимый ресурс — `403`. По истечении срока клиент повторяет вход.

## Порядок реализации

| Этап | Что делаем | Критерий готовности |
|---|---|---|
| 1. Standalone и вход | Запускаем исполняемый сервер Ktor с явной конфигурацией, БД и жизненным циклом. Подключаем создание первого администратора, вход, `GET /api/v1/me` и выход. | Новый процесс встаёт на пустой БД. HTTP-тест проходит создание пользователя, вход, доступ с токеном, перезапуск и отзыв. Защищённые маршруты закрыты по умолчанию. |
| 2. Каталог и воспроизведение | Подключаем папки, сканер и поиск. Даём клиенту исполнителей, альбомы, треки, обложки и поток аудио. | Из временной медиатеки можно получить каталог и проиграть трек. Тесты проверяют полный ответ, `Range`, позиционирование и запрет чтения чужой библиотеки по идентификатору. |
| 3. Пользовательские и административные операции | Добавляем плейлисты, управление пользователями и папками, запуск и статус сканирования. Согласовываем нужные Youamp Desktop сценарии и описываем API в OpenAPI. | Клиентские сценарии проходят по HTTP. Интеграционные тесты подтверждают изоляцию пользователей и разграничение административных прав. |
| 4. Удаление прежнего стека | JSP и его собственные ресурсы удаляем при отделении нового runtime. Вместе с отключением старого сервера убираем Subsonic bindings, прежние HTTP-маршруты, Spring, Servlet/Jasper и WAR-упаковку. Чистим Maven, тесты, команды запуска и образы, сохраняя используемые апи-компонентами ресурсы и нужные миграции БД. | Основной артефакт запускается как standalone Ktor. Защищённые маршруты по-прежнему проверяют права, пути старого API и сайта не обслуживаются. Spring и servlet-зависимости отсутствуют в итоговых артефактах и дереве зависимостей. |

Этапы ведём небольшими коммитами с проверкой изменённого поведения. Отдельный Spring-free WAR и перенос JSP-механизмов входа больше не являются этапами. В переходных коммитах старый запуск может оставаться в дереве до замены, а новый артефакт обслуживает только собственное API.

## Проверки первого среза

- Через HTTP проверить вход, `/api/v1/me`, выход, просроченный и отозванный токены, отсутствие токена и аутентификацию после перезапуска. Попытки аутентификации через query-параметр, cookie и Basic должны возвращать `401`.
- Проверить создание администратора без пароля по умолчанию, одинаковую ошибку для неверных учётных данных, ограничение попыток входа, инвалидирование токенов при смене пароля и недоступность отключённой учётной записи. Срок действия проверять с подставными часами.
- Запускать интеграционные проверки на временной БД, проверять закрытие соединений и остановку standalone-процесса. Проверки в браузере для этого API не требуются.
