# План переноса оставшихся Spring MVC-контроллеров на Ktor

Дата инвентаризации: **15 ноября 2026 года**. Основание: исходники после коммита `f6a0b86` (перенос HomeController). Статусы ниже относятся к выполнению этого плана: наличие существующего Ktor REST не означает, что соответствующая страница уже перенесена.

## 1. Результат, который нужен

Встроенный сайт и внешние приложения получают данные и выполняют действия через Ktor REST. Старые Spring MVC-контроллеры удалены после переноса их сценариев. Стандартные контракты Subsonic/OpenSubsonic сохранены, включая совместимые заглушки удалённого функционала. Адреса страниц и изображений, необходимые сайту и внешним ссылкам, обслуживаются Ktor напрямую или совместимым обработчиком на Ktor.

Переходный JSP допускается как оболочка/шаблон. Он не должен зависеть от Spring MVC-контроллера, формирующего бизнес-данные. Для маленьких шаблонных страниц не создавать REST endpoint, который лишь возвращает переданные клиентом параметры. Настройки и медиаданные получать из существующего REST; новые маршруты добавлять только для недостающих данных.

Завершение плана означает устранение **прикладных Spring MVC-контроллеров**. Spring Security, DI, транзакции, servlet-контейнер и JSP-инфраструктура пока остаются там, где нужны. Их полное удаление потребует следующего самостоятельного плана. Отсутствие `@Controller` само по себе не доказывает полного удаления Spring из HTTP-цепочки.

## 2. Правила исполнения

1. Один исходный контроллер за подход и один отдельный коммит после успешных проверок. Завершающий аудит инфраструктуры — отдельный этап.
2. Перед каждым этапом проверить `git status`, историю и актуальные маршруты. Не включать чужие staged/unstaged изменения. Сейчас отдельно staged удаление `KTOR_MIGRATION_PLAN.md`; этот план его не восстанавливает. `CONTROLLER_MIGRATION_GUIDE.md` — существующая инструкция с устаревшим перечнем кандидатов; фактический остаток приведён здесь.
3. До удаления класса найти все потребители: JSP/JS, includes, параметры ссылок, сервисы, тесты, настройки security, `.view` и внешние подписанные ссылки. Фиксировать также неизвестные сценарии и ограничения.
4. Сначала проверить существующие REST-контракты. Стандартные маршруты не менять ради сайта. Для сайта допустим отдельный endpoint с явным DTO и минимальными данными; не сериализовать `User`, настройки или доменные сущности целиком.
5. В `KtorConfiguration` зарегистрировать все необходимые пути; в `AirsonicKtorServlet` передать контекст пользователя до перехода в корутину и скопировать request-атрибут в `call.attributes`. Новую бизнес-логику держать в сервисах/обработчиках, не раздувать servlet.
6. Проверки прав распространяются и на новый REST endpoint. Для чтения/изменения конкретного файла проверять доступ к его папке; сокрытие кнопки не заменяет серверную проверку. Сохранить существующую CSRF-защиту; не расширять исключения для удобства миграции.
7. Сохранить HTTP-методы существующих Subsonic-контрактов, включая поддерживаемые GET/POST. Новые изменения состояния сайта выполнять подходящим методом с CSRF. Разделять HTTP-ошибки страниц/изображений и Subsonic error envelope.
8. Динамический текст вставлять безопасно; HTML, намеренно разрешённый администратору, учитывать отдельно. Проверять кодировку, кавычки, контекст приложения, URL и обработку ошибки REST, чтобы страница не оставалась молча пустой.
9. Firefox не запускать. Использовать реальные HTTP-интеграционные тесты и необходимые JS-тесты. Отчёт не должен выдавать их за ручную проверку браузера.
10. WebSocket/STOMP не возвращать. Использовать имеющийся обычный REST polling; не строить очередь событий, номера сообщений и серверное состояние клиентов для JSP.
11. После удаления контроллера исключить влияние его старого `.class` в `target/classes` чистой сборкой либо точечным удалением соответствующего сборочного артефакта. Не удалять пользовательские данные.
12. После коммита обновить строку этапа: статус, хеш, выполненные проверки и выявленные ограничения. При фиксации файлов использовать явные пути и `git commit --only -- <пути>`, поскольку в индексе могут быть чужие изменения.

## 4. Детали этапов

### 1. LyricsController

- Сохранить `/lyrics` и `/lyrics.view`, открытие popup, заполнение `artist`/`song`, Unicode и пустые параметры.
- Оболочка читает параметры безопасно; существующий `subsonic-lyrics.js` получает текст через `/rest/getLyrics`. Дополнительный endpoint начальных параметров не нужен.
- Удалить Spring-класс после переключения регистрации страницы на Ktor.
- Проверки: оба адреса с контекстом `/airsonic`, защищённый доступ, фактический REST-ответ с текстом/отсутствием текста, строки с кавычками и HTML. Расширить `LyricsIntegrationTest` и при изменении клиента `subsonic-lyrics.test.cjs`.
- Готово: popup и получение текста работают без старого Spring bean.

### 2. ChangeCoverArtController

- Вынести чтение `id` и исходных значений формы в Ktor, например `/rest/changeCoverArtPage`. Сначала проверить, достаточно ли существующего медиаконтракта.
- Сохранить приоритет явно заданных `artist`/`album` и fallback из файла для отсутствующих/пустых значений; отдельно обработать некорректный, отсутствующий и недоступный `id`.
- Использовать существующие `/rest/searchCoverArt` и `/rest/setCoverArt`; не создавать второй путь сохранения.
- Проверки: разрешённая роль COVERART, отказ обычному пользователю на новом endpoint, недоступная папка, заполнение формы, поиск/назначение обложки с CSRF, отказ без CSRF. База: `CoverArtActionsIntegrationTest`, `subsonic-cover-art.test.cjs`.
- Готово: форма загружается через Ktor, изменение идёт через существующий REST и старый bean отсутствует.

### 3. EditTagsController

- Перенести чтение каталога и построение строк редактора в Ktor `/rest/tagEditor`. Оставить запись в `/rest/editTags`; `/editTags[.view]` обслуживается servlet-оболочкой и больше не зависит от Spring MVC controller.
- Сохранить состав и порядок файлов, `fileName`, `track`, `suggestedTrack`, `title`, `suggestedTitle`, исполнителя, альбом, год и жанр. Значения по умолчанию — из первого файла, список жанров — существующий ID3V1.
- Для пустого каталога возвращать пригодный для формы DTO с пустыми значениями по умолчанию. Не утекать путями файлов за пределами необходимого клиенту имени.
- Проверки: COVERART и доступ к папке на чтение и запись, чужой/отсутствующий id, пустой каталог, спецсимволы, сохранение и перечитывание тегов на изолированных тестовых копиях, CSRF. База: `TagEditIntegrationTest`, `TagEditServiceTest`, `subsonic-tag-edit.test.cjs`.
- Готово: первоначальная загрузка и сохранение редактора не используют Spring MVC; `TagEditIntegrationTest` проверяет DTO, недопустимые id, чужую папку, роль, CSRF и запись тегов в изолированный mp3.

### 4. StarredController

- Сохранить внешний `/rest/getStarred` как есть. Для страницы добавить Ktor DTO `/rest/starredPage`: он передаёт файловые id/имена, разделяет аудио и видео, а также отдаёт только нужные настройки. Не подменять файлы/каталоги ID3-сущностями `/rest/getStarred2`.
- Выявить реально недостающие поля страницы; настройки ролей/party mode/размера обложки/веб-плеера предоставить минимальным DTO либо существующим endpoint. Не повторять всю выборку в новом API без необходимости.
- Сохранить даты добавления в избранное, разделы исполнителей/альбомов/песен/видео, разграничение по пользователю и разрешённым папкам, кнопки воспроизведения/добавления, переходы в альбом и видео.
- Проверки: два пользователя с разным избранным, четыре массива DTO и пустой список, добавление/снятие звезды, party mode, веб-страница без Spring bean. XML/JSON существующего Subsonic API остаются покрыты `StarredIntegrationTest`; клиентский inline JS проверен парсером Node. Ограничение: тестовая медиатека этого интеграционного теста не содержит видеофайла.
- Готово: `/starred[.view]` и начальные данные обслуживает Ktor, DOM-рендер безопасен, действия звёзд/очереди/плейлиста сохранены, Subsonic-схема не менялась, старый Spring bean отсутствует.

### 5. RightController

- `/rest/rightPageSettings` отдаёт только brand, showNowPlaying и поля уведомления; User/Version целиком не сериализуются. Ссылка релиза разрешается только на HTTPS GitHub releases Airsonic Advanced.
- Сохранён приоритет final затем beta. JSP получает конфигурацию из Ktor, scan status опрашивается существующим REST polling, now-playing запускается только при включённой настройке. Данные now-playing строятся через DOM textContent.
- Проверки: `RightPageIntegrationTest` проверил final/beta/нет обновления, две пользовательские настройки, allowlist URL, заголовок no-store, JSP shell и отсутствие Spring bean. Существующий `NowPlayingIntegrationTest` покрывает REST-контракт/polling now-playing. JS в Firefox не запускался; Checkstyle и PMD пропущены в Maven-команде.
- Готово: `/right[.view]` и настройки панели обслуживаются Ktor; `RightController` удалён. Коммит `Move right panel data to Ktor REST`.

### 6. IndexController

- `/rest/indexPageSettings` отдаёт минимальные настройки `showRight`, `showSideBar` и `keyboardShortcutsEnabled`; `autoHidePlayQueue` уже поступает в очередь через её существующий Ktor API, а brand в index shell не используется.

- `main` проходит same-origin/context-path проверку; `javascript:`, внешние адреса и выход из пути приложения заменяются на `nowPlaying.view`. Очередь подключается непосредственно её JSP fragment с существующими Ktor-настройками, без вложенного Spring dispatch и повторной инициализации плеера.
- Проверки: чистая сборка и `IndexPageIntegrationTest`, `KtorServletIntegrationTest`, `WebsiteSettingsIntegrationTest` прошли (15 интеграционных тестов); `index-page.test.cjs` проверил локальные и отклоняемые URL; inline JS прошёл `node --check`. Checkstyle и PMD пропущены; Firefox не запускался.
- Готово: оболочка сайта и её пользовательские настройки обслуживаются Ktor; старый `IndexController` удалён. Коммит `Move index shell to Ktor REST`.

### 7. CoverArtJspController — выполнен

### 8. RatingJspController — выполнен

Интеграционные проверки покрывают страницу, set/clear, CSRF, неверные данные, отсутствие Spring bean/HTML route и сохранность Subsonic-контракта. Checkstyle и PMD пропущены параметрами Maven; Firefox не запускался.

### 9. CoverArtController

- `/rest/getCoverArt` уже напрямую вызывает `CoverArtImageService`. Добавить необходимые старые пути `/coverArt[.view]` и `/ext/coverArt[.view]` к Ktor-обработке с сохранением параметров `id`, `size`, `offset`, MIME и потока байтов.
- Публичный `/ext/coverArt` используется подписанными ссылками public-share. Сохранить внешние URL, проверку JWT и привязку токена к ресурсу/параметрам; не подменять путь redirect-ом, который обесценит подпись. Если текущее поведение неясно — сначала добавить характеризующий тест.
- Проверить фактически действующие cache headers/Last-Modified/условные запросы. Наличие интерфейса `LastModified` не доказывает, что MVC применяет его к аннотированному обработчику. Сохранить наблюдаемое поведение, не предполагать обязательный 304 без проверки.

## 5. Тестовая стратегия и критерии завершения

Тесты запускать **при реализации**, а не при написании этого плана. Имена новых тестов выше — предложения, существующие имена взяты из репозитория. Проверять реальные данные и эффекты; наличие массива или строки `/rest/` в HTML не заменяет проверку содержимого, прав и действий.

Для каждого контроллера обязательны применимые проверки:

- HTTP через запущенное приложение: регистрация Ktor, нужные методы, авторизация/роль, параметры и ошибки, `.view`/без суффикса, контекст `/airsonic`, ответы и побочные эффекты.
- Для новых REST данных — пользовательская изоляция и минимальный DTO; для стандартных Subsonic — прежний XML/JSON envelope и версия через `TestCaseUtils.restApiVersion()`.
- Для изменённого клиента — рендеринг реальных данных, спецсимволы, важные кнопки, сетевые ошибки; для polling — запуск/остановка без дублирования таймеров. Проверять исполняемую JS-логику, а не только текст JSP.
- Для файлов/тегов — тестовые копии и очистка; для внешних сервисов/proxy — локальные fixtures, никакой зависимости теста от доступности внешнего интернета.
- Отсутствие старого Spring bean и зависимостей на удалённый тип; после очистки сборочных артефактов приложение всё ещё запускается.

Использовать доступный Maven и запускать целевые тесты с зависимостями проекта по текущему окружению. После значимых этапов расширять набор только по затронутой области, в финале — общая регрессия. Checkstyle/PMD и прочие проверки не отключать молча: если используется существующий обход из-за отдельного сбоя, указать ограничение. Firefox не запускать.

**Этап выполнен**, когда все найденные нужные сценарии обслуживает Ktor, клиент использует REST для данных/действий, контракты и права подтверждены осмысленными тестами, старый класс и HTTP-делегирование удалены, diff проверен, создан отдельный коммит и здесь записан результат. Незакрытые сценарии и внешние блокировки указывать явно.

**Весь план выполнен**, когда закрыты 14 контроллеров в объёме и инфраструктурный аудит, сохранены необходимые старые URL, стандартные Subsonic ответы и работа сайта, а остаточная зависимость от Spring описана отдельно. `org.airsonic.player.removal` в критерии завершения не входит. Удаление JSP/webapp и Spring Security не выдавать за выполненное без отдельной работы.
