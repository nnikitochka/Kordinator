# План переноса оставшихся Spring MVC-контроллеров на Ktor

Дата инвентаризации: **15 ноября 2026 года**. Основание: исходники после коммита `f6a0b86` (перенос HomeController). Статусы ниже относятся к выполнению этого плана: наличие существующего Ktor REST не означает, что соответствующая страница уже перенесена.

## 1. Результат, который нужен

Встроенный сайт и внешние приложения получают данные и выполняют действия через Ktor REST. Старые Spring MVC-контроллеры удалены после переноса их сценариев. Стандартные контракты Subsonic/OpenSubsonic сохранены, включая совместимые заглушки удалённого функционала. Адреса страниц и изображений, необходимые сайту и внешним ссылкам, обслуживаются Ktor напрямую или совместимым обработчиком на Ktor.

Переходный JSP допускается как оболочка/шаблон. Он не должен зависеть от Spring MVC-контроллера, формирующего бизнес-данные. Для маленьких шаблонных страниц не создавать REST endpoint, который лишь возвращает переданные клиентом параметры. Настройки и медиаданные получать из существующего REST; новые маршруты добавлять только для недостающих данных.

Завершение плана означает устранение **прикладных Spring MVC-контроллеров**. Spring Security, DI, транзакции, servlet-контейнер и JSP-инфраструктура пока остаются там, где нужны. Их полное удаление потребует следующего самостоятельного плана. Отсутствие `@Controller` само по себе не доказывает полного удаления Spring из HTTP-цепочки.

## 2. Правила исполнения

1. Один исходный контроллер за подход и один отдельный коммит после успешных проверок. Завершающий аудит инфраструктуры — отдельный этап.
2. Перед каждым этапом проверить `git status`, историю и актуальные маршруты. Не включать чужие staged/unstaged изменения. Сейчас отдельно staged удаление `KTOR_MIGRATION_PLAN.md`; этот план его не восстанавливает. `CONTROLLER_MIGRATION_GUIDE.md` — существующая инструкция с устаревшим перечнем кандидатов; фактический остаток приведён здесь.
3. До удаления класса найти все потребители: JSP/JS, includes, параметры ссылок, сервисы, тесты, настройки security, `.view` и внешние подписанные ссылки. Фиксировать также неизвестные сценарии и ограничения.
4. Сначала проверить существующие REST-контракты. Стандартные маршруты не менять ради сайта. Для сайта допустим отдельный endpoint с явным DTO и минимальными данными; не сериализовать `User`, настройки или доменные сущности целиком.
5. В `KtorConfiguration` зарегистрировать все необходимые пути; в `AirsonicKtorServlet` передать контекст пользователя до перехода в корутину и скопировать request-атрибут в `call.attributes`. Новую бизнес-логику держать в сервисах/обработчиках, не раздувать servlet.
6. Проверки прав распространяются и на новый REST endpoint. Для чтения/изменения конкретного файла проверять доступ к его папке; сокрытие кнопки не заменяет серверную проверку. Сохранить существующую CSRF-защиту; не расширять исключения для удобства миграции.
7. Сохранить HTTP-методы существующих Subsonic-контрактов, включая поддерживаемые GET/POST. Новые изменения состояния сайта выполнять подходящим методом с CSRF. Разделять HTTP-ошибки страниц/изображений и Subsonic error envelope.
8. Динамический текст вставлять безопасно; HTML, намеренно разрешённый администратору, учитывать отдельно. Проверять кодировку, кавычки, контекст приложения, URL и обработку ошибки REST, чтобы страница не оставалась молча пустой.
9. Firefox не запускать. Использовать реальные HTTP-интеграционные тесты и необходимые JS-тесты. Отчёт не должен выдавать их за ручную проверку браузера.
10. WebSocket/STOMP не возвращать. Использовать имеющийся обычный REST polling; не строить очередь событий, номера сообщений и серверное состояние клиентов для JSP.
11. После удаления контроллера исключить влияние его старого `.class` в `target/classes` чистой сборкой либо точечным удалением соответствующего сборочного артефакта. Не удалять пользовательские данные.
12. После коммита обновить строку этапа: статус, хеш, выполненные проверки и выявленные ограничения. При фиксации файлов использовать явные пути и `git commit --only -- <пути>`, поскольку в индексе могут быть чужие изменения.

## 4. Детали этапов

### 1. LyricsController

- Сохранить `/lyrics` и `/lyrics.view`, открытие popup, заполнение `artist`/`song`, Unicode и пустые параметры.
- Оболочка читает параметры безопасно; существующий `subsonic-lyrics.js` получает текст через `/rest/getLyrics`. Дополнительный endpoint начальных параметров не нужен.
- Удалить Spring-класс после переключения регистрации страницы на Ktor.
- Проверки: оба адреса с контекстом `/airsonic`, защищённый доступ, фактический REST-ответ с текстом/отсутствием текста, строки с кавычками и HTML. Расширить `LyricsIntegrationTest` и при изменении клиента `subsonic-lyrics.test.cjs`.
- Готово: popup и получение текста работают без старого Spring bean.

### 2. ChangeCoverArtController

- Вынести чтение `id` и исходных значений формы в Ktor, например `/rest/changeCoverArtPage`. Сначала проверить, достаточно ли существующего медиаконтракта.
- Сохранить приоритет явно заданных `artist`/`album` и fallback из файла для отсутствующих/пустых значений; отдельно обработать некорректный, отсутствующий и недоступный `id`.
- Использовать существующие `/rest/searchCoverArt` и `/rest/setCoverArt`; не создавать второй путь сохранения.
- Проверки: разрешённая роль COVERART, отказ обычному пользователю на новом endpoint, недоступная папка, заполнение формы, поиск/назначение обложки с CSRF, отказ без CSRF. База: `CoverArtActionsIntegrationTest`, `subsonic-cover-art.test.cjs`.
- Готово: форма загружается через Ktor, изменение идёт через существующий REST и старый bean отсутствует.

### 3. EditTagsController

- Перенести чтение каталога и построение строк редактора в Ktor `/rest/tagEditor`. Оставить запись в `/rest/editTags`; `/editTags[.view]` обслуживается servlet-оболочкой и больше не зависит от Spring MVC controller.
- Сохранить состав и порядок файлов, `fileName`, `track`, `suggestedTrack`, `title`, `suggestedTitle`, исполнителя, альбом, год и жанр. Значения по умолчанию — из первого файла, список жанров — существующий ID3V1.
- Для пустого каталога возвращать пригодный для формы DTO с пустыми значениями по умолчанию. Не утекать путями файлов за пределами необходимого клиенту имени.
- Проверки: COVERART и доступ к папке на чтение и запись, чужой/отсутствующий id, пустой каталог, спецсимволы, сохранение и перечитывание тегов на изолированных тестовых копиях, CSRF. База: `TagEditIntegrationTest`, `TagEditServiceTest`, `subsonic-tag-edit.test.cjs`.
- Готово: первоначальная загрузка и сохранение редактора не используют Spring MVC; `TagEditIntegrationTest` проверяет DTO, недопустимые id, чужую папку, роль, CSRF и запись тегов в изолированный mp3.

### 4. StarredController

- Для содержимого сначала использовать `/rest/getStarred`: текущая страница работает с файловыми id/каталогами. Не подменять их ID3-сущностями `/rest/getStarred2`.
- Выявить реально недостающие поля страницы; настройки ролей/party mode/размера обложки/веб-плеера предоставить минимальным DTO либо существующим endpoint. Не повторять всю выборку в новом API без необходимости.
- Сохранить даты добавления в избранное, разделы исполнителей/альбомов/песен/видео, разграничение по пользователю и разрешённым папкам, кнопки воспроизведения/добавления, переходы в альбом и видео.
- Проверки: два пользователя с разным избранным и правами папок, все четыре раздела, пустой список, только видео, добавление/снятие звезды, party mode, веб/внешний плеер. XML/JSON существующего Subsonic API должны сохранить схему. База: `StarredIntegrationTest`; добавить проверки страницы и клиента.
- Готово: данные и действия избранного обслуживает Ktor, корректные id и пользовательская изоляция подтверждены.

### 5. RightController

- Перенести настройки панели, brand и уведомление о новой версии в минимальный DTO, например `/rest/rightPageSettings`. Не отдавать целиком User/объект версии.
- Сохранить приоритет: разрешённая пользователем final-версия, затем beta. В DTO передать только нужные текст/версию/адрес; проверить происхождение ссылки.
- Использовать уже имеющиеся `getScanStatus` и now-playing клиент с обычным polling. Учитывать `showNowPlaying`: отключённая опция не должна запускать лишний опрос. Не создавать дублирующиеся таймеры при повторной инициализации.
- Проверки: настройки двух пользователей, final/beta/нет обновления через контролируемый VersionService без обращения в интернет, скрытый now playing, scanning→idle, ошибка запроса и восстановление. База: `NowPlayingIntegrationTest` и существующие JS-тесты опроса (точные имена сверить в репозитории).
- Готово: данные панели и её обновления больше не зависят от Spring-контроллера.

### 6. IndexController

- Перенести `showRight`, `autoHidePlayQueue`, `keyboardShortcutsEnabled`, `showSideBar`, brand в Ktor, например `/rest/indexPageSettings`.
- Сохранить имена iframe, ссылки верхней/левой/правой панели, первоначальную навигацию `nowPlaying.view`, очередь и настройку `main`. Проверить, какие из передававшихся полей фактически потребляются include-файлами.
- Начальные параметры навигации не должны позволять вставку HTML или `javascript:`/внешнего URL в iframe. Согласовать допустимые локальные назначения с найденными вызывающими местами.
- При асинхронной загрузке настроек не создавать второй плеер и не запускать очередь дважды. Для отсутствия скачивания `play.m3u` проверить фактический выбор веб-плеера в HTTP-сценарии и клиентскую инициализацию.
- Проверки: `/index`, `/index.view`, переход после login, видимость панелей, настройки двух пользователей, безопасный main, загрузка очереди один раз, неизменность выбранного веб-плеера. Использовать существующий `KtorServletIntegrationTest` и тесты очереди/навигации по затронутым сценариям.
- Готово: оболочка сайта получает настройки через Ktor и сохраняет рабочую навигацию без IndexController.

### 7. CoverArtJspController

- `mediaMain.jsp` и `playlists.jsp` реально запрашивают `/coverArtJsp.view`. Класс пока нельзя удалить как неиспользуемый.
- Предпочтительный результат: общий клиентский рендерер обложки по REST-данным, используемый этими страницами. Сохранить album/playlist id, размеры, подписи, переход/zoom, play/add, режим overflow.
- Если старый маршрут ещё нужен обнаруженным потребителям, оставить совместимый HTML-обработчик на Ktor до удаления всех вызовов. Не называть HTML endpoint REST API; новые клиентские данные и действия идут через REST.
- Проверки: альбом и плейлист, captions с кавычками/HTML, пустая обложка, overlay-действия с правильным id, zoom/change, оба текущих потребителя. Не смешивать этот этап с удалением бинарного CoverArtController.
- Готово: старый Spring bean удалён; все обнаруженные запросы HTML-фрагмента либо заменены клиентским рендерером, либо обслуживаются Ktor.

### 8. RatingJspController

- Перенести отрисовку readonly/editable рейтинга в общий JS, используя существующий REST рейтинга. Сохранить шкалу 0–50 для отображения, 0–5 для команды и половинчатые звёзды.
- Обновить потребителя в `mediaMain.jsp`. Совместимость `/ratingJsp[.view]` решать по фактическим вызовам, при необходимости дать HTML-адаптер на Ktor.
- Проверки: 0/30/35/50, режим без кнопок, set/reset с правильным media id, отказ по роли/CSRF и безопасные параметры фрагмента. Уже есть проверки `/ratingJsp.view` в `KtorServletIntegrationTest`; их обновить осмысленно. База также `RatingIntegrationTest`, `subsonic-rating.test.cjs`.
- Готово: рейтинг отображается и изменяется без Spring MVC-фрагмента.

### 9. CoverArtController

- `/rest/getCoverArt` уже напрямую вызывает `CoverArtImageService`. Добавить необходимые старые пути `/coverArt[.view]` и `/ext/coverArt[.view]` к Ktor-обработке с сохранением параметров `id`, `size`, `offset`, MIME и потока байтов.
- Публичный `/ext/coverArt` используется подписанными ссылками public-share. Сохранить внешние URL, проверку JWT и привязку токена к ресурсу/параметрам; не подменять путь redirect-ом, который обесценит подпись. Если текущее поведение неясно — сначала добавить характеризующий тест.
- Проверить фактически действующие cache headers/Last-Modified/условные запросы. Наличие интерфейса `LastModified` не доказывает, что MVC применяет его к аннотированному обработчику. Сохранить наблюдаемое поведение, не предполагать обязательный 304 без проверки.
- Заменить ссылки на `CoverArtController.*` в REST mapper/playlists существующими константами сервиса; проверить внешние usages `scale` и статических prefix. Не удалять изображения/кеши пользователей.
- `CoverArtRestIntegrationTest` содержит spy на удаляемый MVC-класс — заменить его проверками результата и отсутствия Spring bean, не оставлять зависимость от удалённого типа.
- Проверки: стандартные XML/JSON связанные контракты не меняются; бинарные байты/MIME GET и HEAD, все поддерживаемые префиксы id, offset/size, отсутствующий ресурс; старые пути; public share с валидным/просроченным/чужим JWT и подменой id. База: `CoverArtRestIntegrationTest`, `CoverArtImageServiceTest` и тесты share.
- Готово: все необходимые адреса изображений обслуживает Ktor без ссылок на старый класс.

### 10. AvatarController

- Расширить существующую Ktor-реализацию `AvatarRestController` совместимыми `/avatar` и `/avatar.view`. Использовать общий выбор/чтение изображения без копирования алгоритма.
- Сохранить приоритет system id, выбор по username, CUSTOM/NONE/system, `forceCustom`, classpath/webapp/file-ресурсы, MIME и отсутствие картинки.
- Проверить действующие правила доступа и кеширования старых адресов, изменение аватара/настроек пользователя, HEAD/условные запросы. Не расширять публичный доступ ради картинок.
- Проверки: все схемы, принудительный custom, неверный id/forceCustom, отсутствующий файл, обновление custom после загрузки; отдельная регрессия стандартного `/rest/getAvatar`. База: `AvatarRestIntegrationTest`, `AvatarUploadIntegrationTest`.
- Готово: website и стандартный API используют Ktor, старый Spring bean удалён.

### 11. ProxyController

- Сохранить `/proxy` и `/proxy.view` как совместимый Ktor endpoint. Его удаление без отдельного решения не входит в план: существующее журналирование введено для оценки неизвестных старых клиентов.
- Вынести HTTP-загрузку в сервис, сохранить обязательный `url`, поток байтов, timeout и наблюдаемую обработку ошибок upstream/redirect. Конкретные сетевые/timeout исключения охарактеризовать до переноса.
- Сохранить запись о каждом вызове, включая некорректный, без url, query, токенов и credentials в логах. Не менять политику допустимых upstream-адресов молча в рамках миграции; ограничения, если нужны, оформить отдельно.
- Проверки на локальном HTTP fixture: байты успешного ответа, upstream 404/500, отсутствие url, timeout/обрыв, действующая авторизация, оба пути и журналирование без секретов. Перенести `ProxyControllerTest` на сервис/Ktor HTTP, не обращаться к внешнему интернету.
- Готово: совместимый proxy работает на Ktor; Spring-класс удалён, неизвестные клиенты не теряют адрес.

### 12. PodcastRemovalController

- Сохранить совместимость удалённых подкастов; не возвращать функциональность подкастов и не удалять API-заглушки.
- Перенести GET/POST `/rest/getPodcasts`, `/rest/getNewestPodcasts`, `/rest/refreshPodcasts`, `/rest/createPodcastChannel`, `/rest/deletePodcastChannel`, `/rest/deletePodcastEpisode`, `/rest/downloadPodcastEpisode`, `/rest/exportPodcasts/opml` и действующие `.view`-варианты.
- Getters сохраняют пустые успешные Subsonic payloads; пять изменяющих операций — прежний `NOT_AUTHORIZED` и сообщение. OPML — отдельный XML-документ, не Subsonic envelope: сохранить наблюдаемую структуру `PodcastExportOPML`, title/date/version, MIME и `Content-Disposition` с `airsonic.opml`.
- Переиспользовать JAXBWriter/действующие DTO либо точную совместимую сериализацию без MVC `ResponseEntity`. `PodcastExportOPML` можно оставить как DTO; не удалять его вместе с контроллером автоматически.
- Проверки: оба метода и суффиксы, XML/JSON для Subsonic, version/status/error code/message, авторизация, OPML как XML со структурой и заголовками. Создать `PodcastCompatibilityIntegrationTest`; отсутствие найденного существующего теста не означает отсутствие внешних клиентов.
- Готово: все 8 операций работают без Spring MVC, прежние ответы подтверждены.

### 13. LoginController

- Разделить перенос GET-представления и механизм аутентификации. GET `/login` обслуживает Ktor; POST `/login`, logout, remember-me, session fixation и CSRF продолжают проходить существующую security filter chain. Полная миграция Spring Security не является частью этого этапа.
- Сохранить brand, loginMessage, logout/error-состояния, предупреждение о стандартном admin. Начальные публичные данные отдавать минимально; если нужен REST, публичность разрешать только конкретному маршруту, не всему `/rest/**`.
- Исследовать legacy-параметры `user`/`password` и redirect к `j_username`/`j_password`: воспроизводить фактическую цепочку, не считать GET аутентификацией. Не логировать секреты. Любое изменение этого поведения описать отдельно.
- Проверки: анонимный GET страницы, токен CSRF в форме, успешный/ошибочный POST с session cookies, отсутствие CSRF, logout, remember-me по фактической конфигурации, переход на `/index`, контекст приложения и сохранение данных формы. Использовать/расширить HTTP login helper из существующих интеграционных тестов.
- Готово: LoginController удалён, вход/выход и его сообщения работают через сохранённую security chain и Ktor-страницу.

### 14. AccessDeniedController

- Перенести `/accessDenied[.view]` как Ktor-страницу, сохранить нужное журналирование без секретов. Не добавлять отдельный REST ради статичного текста ошибки.
- Отличать прямой запрос страницы от error/forward dispatch: реальный отказ в API должен сохранять своё тело и HTTP-статус, не превращаться в успешный HTML.
- Проверки: доступ анонимного пользователя по действующей конфигурации, прямой запрос и реальный отказ роли, контекст `/airsonic`, отсутствие redirect loop; 403/Subsonic ошибки остаются корректными.
- Готово: страница не зависит от Spring-класса, реальный сценарий отказа подтверждён.

### 15. NotFoundController

- Перенести `/notFound[.view]` как Ktor-страницу. Сначала выяснить, какие реальные not-found цепочки вызывают её; не считать её обработчиком всех 404 по имени класса.
- Проверки: прямой URL, неизвестный URL страницы, неизвестный REST endpoint и отсутствующее изображение. Зафиксировать исходные статусы и не превращать API-ошибки в HTML/HTTP 200.
- Готово: представление и найденные вызовы не требуют Spring-класса.

### 16. Завершающий аудит инфраструктуры

- Повторить поиск по всему приложению, включая пакеты вне `controller`: `@Controller`, `@RestController`, mappings, `HttpRequestHandler`, программные mappings и вызовы удалённых классов. Отдельно учитывать framework-контроллеры Boot (`/error` и др.).
- Проверить каждый необходимый старый адрес с суффиксом и без, методы, servlet mapping, FORWARD/INCLUDE/ERROR, context path и static resources. Прямые Ktor-пути не должны зависеть от MVC suffix-forward.
- Проверить `LegacyViewSuffixHandlerMapping`, `LoggingExceptionResolver`, ViewResolver/JstlView, Spring-теги/JSTL/locale/theme, обработку статики и Boot `/error`. Для каждого указать: удаляется сейчас, остаётся ради JSP/framework или требует следующего этапа. Не удалять `ServletConfiguration` целиком: там также фильтры кодировки, REST, cache, bootstrap и метрики.

- Прогнать регрессии по входу/навигации, очереди/выбору плеера, streaming/HLS/download, public shares, аватарам/обложкам и Subsonic XML/JSON. Отдельно проверить отсутствие возвращённых STOMP/WebSocket-зависимостей.
- Итоговый документ должен содержать перечень остаточных зависимостей Spring и следующий объём работ для полного отключения MVC/сервлетного окружения, если они ещё нужны.

## 5. Тестовая стратегия и критерии завершения

Тесты запускать **при реализации**, а не при написании этого плана. Имена новых тестов выше — предложения, существующие имена взяты из репозитория. Проверять реальные данные и эффекты; наличие массива или строки `/rest/` в HTML не заменяет проверку содержимого, прав и действий.

Для каждого контроллера обязательны применимые проверки:

- HTTP через запущенное приложение: регистрация Ktor, нужные методы, авторизация/роль, параметры и ошибки, `.view`/без суффикса, контекст `/airsonic`, ответы и побочные эффекты.
- Для новых REST данных — пользовательская изоляция и минимальный DTO; для стандартных Subsonic — прежний XML/JSON envelope и версия через `TestCaseUtils.restApiVersion()`.
- Для изменённого клиента — рендеринг реальных данных, спецсимволы, важные кнопки, сетевые ошибки; для polling — запуск/остановка без дублирования таймеров. Проверять исполняемую JS-логику, а не только текст JSP.
- Для файлов/тегов — тестовые копии и очистка; для внешних сервисов/proxy — локальные fixtures, никакой зависимости теста от доступности внешнего интернета.
- Отсутствие старого Spring bean и зависимостей на удалённый тип; после очистки сборочных артефактов приложение всё ещё запускается.

Использовать доступный Maven и запускать целевые тесты с зависимостями проекта по текущему окружению. После значимых этапов расширять набор только по затронутой области, в финале — общая регрессия. Checkstyle/PMD и прочие проверки не отключать молча: если используется существующий обход из-за отдельного сбоя, указать ограничение. Firefox не запускать.
