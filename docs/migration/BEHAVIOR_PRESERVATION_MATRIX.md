# Матрица сохранения поведения при удалении Spring и Servlet

Матрица сравнивает функции, которые старый `AirsonicKtorServlet` передавал Spring-контроллерам, с API standalone Ktor. Внешний формат Subsonic не является требованием; пользовательское поведение и операции над медиатекой остаются требованиями, если явно не решено иное.

`KtorApplication.main` запускает именно `standaloneModule`. Метод `Application.module()` регистрирует только внутренний `GET /internal/ktor/ping` и не является production API. Старые Subsonic app-specific credentials и операции с их JWT/encryption keys не переносятся: их заменяет локальная аутентификация Kordinator с серверной bearer-сессией, logout и сменой/сбросом пароля. HLS и jukebox доступны через новые bearer-маршруты. Диагностические health, path watchers, scheduled tasks, cache и transfer statistics перенесены в admin-only endpoints; общие, transcoding, advanced, DLNA, database, library/scanner и настройки серверных плееров доступны через Ktor. Запись тегов в аудиофайлы намеренно исключена как небезопасная для read-only медиатеки. Удаление библиотеки использует старый soft-delete: непустая библиотека теряет индексированные записи, поэтому этот destructive behavior требует осознанного использования.

## Аудит оставшихся старых REST-функций

Это не обещание сохранить каждый старый маршрут. Здесь зафиксировано решение по пользовательской функции: перенести её в новый API, считать уже заменённой другим сценарием либо исключить. Старый URL и Subsonic-формат не являются критерием дизайна.

| Старая функция | Состояние в standalone Ktor | Решение для нового API |
|---|---|---|
| `getAlbumInfo`, `getArtistInfo` | Биография исполнителя и заметки альбома доступны через `GET /api/v1/tracks/{id}/metadata`; похожие треки доступны отдельно | Функция перенесена как metadata ресурса трека, с проверкой доступа к библиотеке и приватным кешем на 5 минут. Нет legacy XML/формата и нет зависимости от старых Spring-контроллеров |
| `setMediaFileComment` | Старый `/rest/setMediaFileComment` и его неиспользуемый контроллер удалены; вместо общего комментария доступна приватная заметка аккаунта через `GET`, `PUT`, `DELETE /api/v1/tracks/{id}/note` | Пользовательские заметки хранятся отдельно от тегов файла и общего каталога и ограничены доступом аккаунта к библиотеке |

Production HTTP routes регистрируются из `KtorApplication.kt` внутри `standaloneModule`; сюда входят как обработчики, объявленные непосредственно в модуле, так и route-классы, явно вызванные из bearer-authenticated группы. Несколько прежних `Kordinator*Routes` (auth, playlist, artist, search, track и album) и их factories/tests не были подключены к production и использовали старые core services/identity callbacks. Они удалены; API-поведение проверяется интеграционными тестами production module (`KtorStandalonePlaylistTest`, `KtorStandaloneRealScanIsolationTest`, `KtorStandaloneAuthTest` и соответствующие admin/media suites). `KordinatorLibraryRoutesTest` и аналогичные изолированные тесты сами по себе не считаются доказательством endpoint-доступности.

## Правило миграции

Для каждой области перед удалением Spring/Servlet-кода:

1. Найти старый маршрут, controller, service и DAO, где выполняется операция.
2. Отделить бизнес-логику и работу с данными от HTTP/Servlet/Spring glue.
3. Подключить существующую логику к standalone Ktor либо перенести её без сужения поведения.
4. Добавить тесты на успешный сценарий, ошибки и права доступа.
5. Только после этого удалить старую точку входа и её framework-зависимости.

Текущие standalone endpoint-ы и их тесты подтверждают только перечисленный функционал. Они сами по себе не доказывают перенос всего приложения или совместное использование прежней базы данных.

### Удалённая обвязка диагностики

`ServerHealthController` (`/rest/getServerHealth`) и его фабрика удалены: диагностика компонентов обслуживается зарегистрированным `GET /api/v1/admin/health`. Общие health contributors и status aggregator сохранены для активного API. `KtorStandaloneHealthTest` проверяет административные права, отсутствие подробностей в публичном health, `Cache-Control: no-store` и `404` старого адреса.

### Удалена серверная локализация старого сайта

`LocaleService`, его фабрики и зависимости в конструкторе `MediaFileService` удалены. Последний потребитель текстовых переводов — незарегистрированный Subsonic `PlaylistsController` — удалён вместе с request DTO; активные операции плейлистов остаются в `/api/v1/playlists`. Удалены `ResourceBundle_*.properties`, вспомогательная утилита сравнения переводов и Maven-копирование английского bundle. Оставшийся старый `MediaFileEntry` форматирует размер файла с `Locale.ENGLISH`, без чтения пользовательских настроек. `locales.txt` пока нужен для списка допустимых настроек языка в действующем API; он не содержит текстовых переводов.

### Аудиотранскодирование в активном API

`GET/HEAD /api/v1/tracks/{id}/stream?format=mp3&bitrateKbps=128` выбирает настроенный профиль `TranscodingService` по исходному и целевому формату, без создания старых User/Player. Для MP3 → MP3 без отдельного профиля используется существующая команда downsampling. Поддерживаются целевые mp3, opus, ogg, aac, flac и wav при наличии соответствующего профиля. Если указан только bitrate, целевой формат — mp3; если только format, битрейт — 192 kbps. Допустимый битрейт — 32–320 kbps. Без этих параметров выдаётся оригинал.

Транскодированный поток не использует ETag исходного файла, неизвестную длину не подменяет оценкой, возвращает `Accept-Ranges: none` и `Cache-Control: private, no-store`. Byte Range для преобразования возвращает `400`; временная перемотка задаётся параметром `startSeconds` (в том числе дробным). Несуществующий профиль возвращает `406`, ошибка запуска процесса — `503`, без подмены оригинальным файлом. `HEAD` проверяет профиль без запуска процесса.

`KtorStandaloneScanTest` проверяет зарегистрированный маршрут, параметры, права, MIME, HEAD, отключение исходных validators и ошибки. `StandaloneAudioTranscodingServiceTest` проверяет реальное WAV → MP3 и декодирование результата через FFmpeg, отсутствие fallback при ошибке запуска и остановку обоих процессов при закрытии цепочки. Проверка с FFmpeg пропускается, если `/usr/bin/ffmpeg` отсутствует.

### Завершение стриминга: временная позиция и жизненный цикл

`GET/HEAD /api/v1/tracks/{id}/stream?format=mp3&bitrateKbps=128&startSeconds=42.5` начинает преобразованный поток с указанной позиции. `startSeconds` должен быть конечным неотрицательным числом; положительная позиция требует известной длительности и должна быть строго меньше неё. При указании только позиции используется MP3, 192 kbps. FFmpeg получает `-ss` до входного файла, а пользовательские профили могут использовать `%o` в первом шаге. Неподдерживающий перемотку профиль возвращает `406`. Позиция применяется только на первом шаге цепочки и работает также для MP3 downsampling.

Перед отправкой успешного ответа сервер ждёт первые аудиобайты до 30 секунд. Пустой результат и ошибка чтения до начала ответа дают `503`. На маршруте стриминга установлен `HttpRequestLifecycle(cancelCallOnClose = true)`. Отмена HTTP-запроса закрывает поток даже при заблокированном чтении; процессы цепочки завершаются, при необходимости принудительно. Ошибка чтения уже начатой передачи прерывает её; успешная выдача заголовков не гарантирует завершения кодирования.

Для оригинала сохраняются байтовые диапазоны. `If-Range` с совпавшим Last-Modified разрешает `206`; несовпавший/некорректный валидатор или слабый ETag приводят к полному `200`. Тесты проверяют точное совпадение декодированных PCM-сэмплов после дробной перемотки через FFmpeg, `%o`, MP3 downsampling, права, ошибки позиции, HEAD, If-Range и закрытие заблокированного процесса. Разрыв до получения первых байтов дополнительно проверяется настоящим TCP-соединением с Netty на loopback-интерфейсе, без браузера.

### Удалена старая HTTP-обвязка стриминга

Удалены `StreamRestController`, не подключённый `KordinatorTrackStreamRoutes`, старые HLS REST-контроллеры и их фабрики. Вместе с ними удалены `MediaStreamService`, `HlsPlaylistService` и `HlsSegmentService`: production Ktor их не использовал, а видео HLS уже реализован bearer-scoped `StandaloneVideoPlaybackService` через `HlsSession` и `TranscodingService`. Аудио выдаётся активным `/api/v1/tracks/{id}/stream`, включая прямой файл, транскодирование, перемотку и HTTP Range для оригинала. Удалены тесты старых маршрутов и устаревших сервисов; новые проверки `KtorStandaloneScanTest`, `KtorStandaloneVideoTest` и `StandaloneAudioTranscodingServiceTest` покрывают активные сценарии.
