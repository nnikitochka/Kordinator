# Spring removal baseline: static inventory

**Baseline:** repository `HEAD 71b47a3167f96beb7f153cbe8642b16bea62723a`, 2026-11-16. This document is a source/configuration inventory, not a runtime characterization. Maven, tests, and application startup were not run for this slice. Counts are reproducible line/file matches from [`inventory.py`](inventory.py) (`python3 inventory.py --revision 71b47a3`); structured details are in [`spring-inventory.json`](spring-inventory.json). The script reads the selected immutable Git archive (default revision `HEAD`; the checked snapshot uses the full SHA above) and excludes `.git`, `target`, `.run`, local Maven `repo/`, `.idea`, docs, and Markdown. It scans project source/config in the remaining repository; line counts include comments and config strings and are not AST counts.

## Annotation and API inventory

The scanner records candidate lines by category (see JSON for paths and line numbers). Important runtime findings:

| Concern | Static locations and semantics |
|---|---|
| DI/config | Spring stereotypes and `@Bean` graph are widespread. `KtorConfiguration` is a large explicit registration method: it constructs `ServletRegistrationBean<ServletApplicationEngine>`, passes many controllers/services and wires context path/error handling; despite explicit method params, bean creation still depends on Spring. `SettingsService` receives Spring `Environment` and `PropertySource`. |
| JDBC | DAO layer uses Spring JDBC helpers (`AbstractDao` and DAO subclasses), Spring `DataSource`/transaction manager wiring. `CredentialsManagementController.kt` also directly creates a Spring `TransactionTemplate`. |
| Transactions | `Application` enables transaction management with `AdviceMode.ASPECTJ`; `@EnableTransactionManagement(mode=ASPECTJ)` means woven/self-invocation behavior can be relevant, and must not be replaced on the assumption of proxy-only semantics. Nine method annotations explicitly request `READ_COMMITTED`: `AlbumDao`, `ArtistDao`, three methods in `MusicFolderDao`, `MediaFileDao`, `AvatarDao`, and two in `CoverArtDao`. Unqualified annotations occur on `PlaylistDao`, `TranscodingDao`, `ShareDao`, two `PlayQueueDao` methods, and class-level `UserDao`; they use the configured/default isolation. `BookmarkDao` uses a `TransactionTemplate` and sets `ISOLATION_READ_COMMITTED`. `CredentialsManagementController.kt` has another transaction template; its requested defaults/operations should be characterized from method body/runtime. Annotation presence does not prove effective transaction boundary, rollback, or propagation behavior. |
| Cache | `CacheConfiguration` enables caching in `AdviceMode.ASPECTJ` (comment explicitly says self calls are expected to be advised). Seven Ehcache/JCache regions, all max heap 1,000 entries: `userCache` 2d TTL, `userSettingsCache` 2d, `mediaFilePathCache` 2h, `mediaFileIdCache` 2h, `coverArtCache` 2d, `playlistCache` 10d, `playlistUsersCache` 10d. In particular: SecurityService username key (caseSensitive condition, null excluded); SettingsService username; media path=`relativePath-folder.id`, ID key; cover art=`type-id`; playlist and playlist-user use method argument/default keys. These method-cache annotations do not declare their own TTL; region expiry above applies. `LastFmCache` is a separate non-Spring cache with constructor TTL, not an Ehcache Spring-cache region. |
| Lifecycle | Scanner sees 18 matching lifecycle candidate lines across scanned scope. Production `@PostConstruct` setup occurs in `DatabaseService`, `SettingsService`, `StatusService`, `MediaScannerService`, `CoverArtImageService`, `HlsSegmentService`, `UPnPService`, `PlaylistService`, `PlayerService`, and several DAOs (`PlaylistDao`, `MusicFolderDao`, `BookmarkDao`, `CoverArtDao`, `PlayQueueDao`, `ShareDao`, `TranscodingDao`, `PlayerDao`). Some work starts jobs/watchers/indexes; inspect each body before moving lifecycle. No production `@PreDestroy` was found. `TaskSchedulingService` builds a daemon `ThreadPoolTaskScheduler`, calls `afterPropertiesSet`, and retains it only via `ScheduledTaskRegistrar`; no visible shutdown/close path is present. This is a lifecycle gap to characterize, not evidence of clean shutdown. |
| Scheduling | `TaskSchedulingService` supports named fixed-delay, fixed-rate, and once tasks; replacement cancels existing handle when `cancelIfExists`; one-shot trigger returns null after first completed execution. Default interval is Spring-configured pool size 10. Scheduled-task snapshot timestamps are estimates; fixed-delay last/next are explicitly unknown estimates. `DatabaseService.init()` catches/logs any throwable from schedule. Automatic HSQL backup first runs after 5 min then fixed-rate every configured hours (`-1` disables); default/negative/zero behavior needs runtime/config validation. |
| Method security | `GlobalSecurityConfig` enables `@EnableMethodSecurity(securedEnabled=true)`; scan found no production `@Secured`/`@PreAuthorize` usage. Primary authorization is HTTP path rules plus service-level checks. Do not infer method-security behavior is unused until complete scan confirms generated/reflected paths. |

## JSP and HTTP security contract (static only)

The JSP shared include declares `spring`, `form`, and `sec` aliases. Production usage is dominated by 135 `<spring:theme>` calls (theme resource resolution); six `<sec:csrfInput>` calls emit CSRF form tokens; one `<sec:authorize>` gates a view fragment. JSPs depend on container/Jasper and still import Spring tag libs via `WEB-INF/jsp/include.jsp`.

`GlobalSecurityConfig` defines two ordered filter chains. `/ext/**` is stateless; JWT parameter processing, custom REST endpoints for stream/coverArt/share/HLS/captions allow roles TEMP/USER and all remaining ext endpoints require authentication. Main chain enables CORS, HTTP Basic, REST parameter auth after Basic, CSRF matcher, same-origin frame headers, public login/recovery/static paths, role-specific settings/admin/playlist/upload/share/cover-art paths, then USER for `/**`. Login form uses `/login`, `j_username`, `j_password`, success `/index`, failure `/login?error`; logout deletes `JSESSIONID` and `XSRF-TOKEN`, clears auth, invalidates session, then `/login?logout`; remember-me uses configurable key (null means ephemeral key per comment). CORS allows wildcard origin/method on selected REST/stream/HLS/captions paths. Password encoder map includes legacy and current formats plus persisted AES-GCM key/salt setup; replacing it requires fixture parity, not just a new encoder.

CSRF matcher exempts safe methods GET/HEAD/TRACE/OPTIONS, POST `/rest/.*\.view` (including matcher query allowance), and POST `/search` or `/search.view`; other methods/paths require CSRF. Confirm path normalization under servlet context path and actual cookie attributes/samesite/secure/httpOnly, token repository details, filter-chain match behavior, auth precedence (session vs Basic vs Subsonic `u/p`, `t/s`, JWT), challenge/status/error responses, and public/share link behavior at runtime. Static configuration establishes choices but not final observable contract.

## Configuration and reflection names

`CustomPropertySourceConfigurer` comment and implementation specify precedence (highest to lowest): Spring CLI args, JVM properties, environment, `application.properties`, `airsonic.properties`, defaults; it migrates aliases from ordered property sources, appends migrated props and places defaults first. `SettingsService` contains legacy keys including `spring.datasource.*` and `spring.liquibase.*`; the immutable scan records 70 Spring-named property/environment alias matches separately. These are config compatibility candidates, not proof of Spring API/runtime binding. Exact precedence when the same key occurs under original and migrated alias, empty/invalid values, `addFirst` defaults and SpEL/Boot config processing require characterization tests.

Reflection/factory strings include Boot Tomcat factory, `TomcatApplication`, `spring.factories`, Spring property keys and the Liquibase FQCN list above. Full source-level match details are in JSON. There is no claim here that reflection scan covers generated bytecode, packaged WAR, nested JARs, or runtime service loading.

## What static inspection does not establish

- Effective Maven graph, dependency/plugin scopes, generated weaving, packaged WAR contents, runtime bean graph, and actual JVM version support.
- Real transaction begin/commit/rollback timing, proxy/weaving hit paths, propagation, connection reuse, isolation per operation, commit failure behavior, or transaction/cache invalidation ordering.
- Cache hit rates, runtime expiry, eviction races, heap pressure, persistence/restart semantics, or cache keys after SpEL evaluation.
- Scheduler thread ownership, execution overlap/cancellation timing, task exception handling, and shutdown behavior.
- HSQL conversion behavior on a representative existing database, Liquibase execution ordering/checksum behavior on existing DBs, or failed-start cleanup.
- HTTP behavior under deployed context path `/airsonic`, actual cookie flags, authentication selection, CSRF status/body, error pages, CORS preflight, redirects, and role/folder authorization.
- Whether service constructors, lifecycle callbacks, datasource initialization, config callbacks, and index/watchers are ordered safely under Boot.

These need executable WAR/process evidence, integration fixtures, logs or debugger/runtime observation. No tests or Maven commands were run in this static-inventory task.
