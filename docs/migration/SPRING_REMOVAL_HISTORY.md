# История миграции Spring и старый план

Действующая цель описана в [плане самостоятельного музыкального бэкенда](../../SPRING_REMOVAL_PLAN.md). Ниже сохранены прежние этапы, результаты проверок и коммиты.

Дата базового аудита: **16 ноября 2026 года**. Документ описывает целевой путь от текущего Ktor-on-servlet приложения к приложению без Spring, с отдельным шлюзом от сохранённого JSP-сайта к standalone Ktor. Ниже ведётся журнал подтверждённых изменений; незавершённые или не проверенные срезы не считаются закрытыми этапами.

## 1. Цель, границы и решения

Цель — удалить Spring Framework, Spring Boot, Spring Security, Spring Data/JDBC helpers, Spring Cache, Actuator, интеграционные плагины и тестовые зависимости из production, тестов, инструментов сборки и упаковки. По окончании сохраняются пользовательские HTTP/API/потоковые контракты и поддерживаемые способы запуска, а runtime wiring становится явным.

Целевой первый runtime — **Spring-free Tomcat/Jasper servlet WAR**, подключающий Ktor servlet и временный JSP bridge. Это позволяет удалить Spring, не объявляя переписывание всего сайта условием первого результата. Второй, отдельный target — **standalone Ktor JVM**, который не использует servlet API, Tomcat или JSP. Первая цель сама по себе не является доказательством standalone engine: M2 считается завершённым только после независимого запуска Ktor без servlet adapter и полного прохождения его критериев.

Предлагаемые архитектурные решения для реализации:

- Композиционный корень с явным constructor wiring; не вводить новый тяжёлый DI-контейнер.
- Сохранить JDBC, текущий `DataSource`, SQL и схему. Не совмещать удаление Spring с заменой ORM, перестройкой запросов или миграцией БД.
- Сохранить используемые Ehcache/JCache и Micrometer без Spring-адаптеров. Версии библиотек не повышать в рамках этой работы.
- Запускать Liquibase напрямую. При переносе/переименовании классов, упомянутых в исторических changeset, сохранять их FQCN или обеспечить совместимое разрешение старого имени.
- Перенести аутентификацию, авторизацию и crypto на framework-free код с поддерживаемыми примитивами и доказать parity на fixture-тестах. Не перехешировать и не перешифровывать сохранённые credentials вслепую.
- Оставить Jackson и JAXB, пока не доказано сохранение внешних форматов. Maven оставить; Spring Boot parent/BOM убрать только в завершающей фазе, закрепив версии реально используемых плагинов и зависимостей.
- Сначала перейти на Spring-free servlet/Tomcat bootstrap и сохранить JSP. Standalone Ktor — самостоятельный шлюз после отдельной проверки всех servlet-зависимостей и замены JSP/UI либо явного решения отказаться от JSP. Не вводить частный loopback API ради временного JSP.
- Java→Kotlin rewrite **не является prerequisite** удаления Spring. Новую инфраструктуру можно писать на Kotlin; небольшие Java-классы переписывать только по необходимости.

Миграция должна идти небольшими коммитами, по одному подсистемному срезу с тестом поведения. Один этап может потребовать нескольких небольших коммитов; не объединять его целиком в один крупный commit. Допускаются две реализации только в изолированных тестах или ограниченном переходном adapter. Не запускать одновременно две копии job, два кэша с разными invalidation правилами, две security chain или обходную авторизацию.

### Поведенческие контракты, которые нельзя ослаблять

- REST: JSON/XML форма, null/omitted attributes, DTO/ID, `discNumber`, JSONP, Subsonic error envelope, версии, заголовки, GET/POST и legacy `.view` aliases. Отдельно проверить Ktor и JSP bridge с context path `/airsonic`.
- Media: stream bytes, `Content-Range`/Range/If-Range, HLS playlist и segments, signed URL, download headers, MIME, HEAD, cache/conditional response; saved queue и live queue остаются разными сценариями.
- Публичные ответы и страницы: locale/theme, session cookie, login/logout/remember-me, CSRF; POST исключения для `/rest/.*\.view` и `/search[.view]`, остальные unsafe methods требуют токен. CORS и доступ к upload/chunk endpoints сохраняются вместе с размерами/лимитами.
- Безопасность: Basic, Subsonic `u/p` и `t/s`, `enc:` password, текущие варианты кодирования/сравнения, LDAP, JWT для `/ext`, stateless public-share/HLS signed links, роли и folder access. Запрос не должен получать права только из client-supplied identity.
- Ошибки и утечки: исходные HTTP status/error body, путь без query string там, где он отражается/логируется, отсутствие credentials/tokens/query в логах, CSP/cache/error headers и корректное поведение неизвестных URL.
- Blocking JDBC внутри Ktor coroutines: не выполнять блокирующий DAO на event loop. Выделить bounded IO dispatcher/executor или эквивалентную уже имеющуюся инфраструктуру и обеспечить ограничение/закрытие; не передавать transaction context через coroutine suspension/thread hop.

### Порядок запуска и остановки нового runtime

Порядок для этапов 3, 4, 6, 11 и 12 зафиксировать одной явной последовательностью: загрузка и проверка конфигурации → настройка логирования → проверка/резервная копия и upgrade legacy HSQL до открытия основного пула → создание DataSource → Liquibase update с историческими параметрами → создание DAO/сервисов/кеша → инициализация индексов и нужных ресурсов → готовность HTTP → разрешение фоновых задач. Фактические зависимости сервисов уточнить на этапе 0; задачи не должны читать недомигрированную схему. Readiness до завершения обязательной инициализации не означает готовность принимать пользовательские запросы.

У каждой стадии есть владелец ресурса и обратная операция закрытия. При ошибке запуска закрыть уже открытые ресурсы и завершить процесс с ненулевым кодом; не оставлять наполовину готовый сервер. При shutdown прекратить приём новых работ, ограниченно дождаться активных операций, отменить фоновые задачи и закрыть watchers, поисковые индексы, транскодеры/внешние процессы, кеш, пул и executor в порядке зависимостей. Проверять также ошибку старта между двумя стадиями, повторный старт и cleanup временных файлов. Изменение схемы не откатывается простым откатом бинарника: перед upgrade нужна копия БД и проверенная процедура восстановления, а не обещание автоматического downgrade Liquibase.

### Gate M1 — Spring-free servlet с работающим сайтом

M1 закрывает практическую цель «удалить Spring и оставить текущий JSP-сайт». Необходимы завершённые этапы 0–13: deployable WAR на Tomcat/Jasper, JSP без Spring tags/runtime, Ktor REST/media, session/auth/CSRF, database upgrade и rollback, jobs, health/metrics, logging/config и все поддерживаемые DB. Финальный BOM/dep tree/war scan доказывает отсутствие Spring в production, test, transitives и build plugins. Tomcat и JSP здесь остаются намеренно; это не standalone Ktor.

### Gate M2 — standalone Ktor

M2 закрывается только после этапа 14: process запускается сам, без Servlet API и web container. Все публичные HTTP контракты работают через новый engine. По умолчанию до M2 заменяется JSP/UI или принимается отдельное явное решение отказаться от него. Если JSP остаётся отдельным optional deployment, он использует уже существующий публичный REST, собственный lifecycle и не содержит второй бизнес-реализации. Наличие выбранного/запущенного JSP servlet runtime означает, что развёрнутое приложение всё ещё Servlet-based; оно не является standalone runtime.

### Gate M3 — Kotlin

M3 — отдельная серия переносов с проверяемой Java/Kotlin совместимостью. Переход на Kotlin не должен задерживать Spring-free servlet target или маскировать неполноту M1/M2.

## 5. Условия остановки миграции и критерий «Spring удалён»

Этап нельзя пометить готовым на основании того, что приложение «собирается». Он закрывается при одновременно зелёных проверках поведения и отсутствии его framework binding. При смене поведения сначала зафиксировать исходное наблюдение, решить совместимость отдельным решением, покрыть тестом и только потом менять контракт.

Финальный аудит M1/M2 должен показать отсутствие во всех модулях и артефактах (включая `integration-test`, tools, tests и packaging), с проверкой по artifact groups и рекурсивных dependency edges, а не только по видимым imports:

- `org.springframework.*`, `org.springframework.boot.*`, `org.springframework.security.*`, `spring-aspects`, Spring Cache/Actuator/API в `src/main`, `src/test`, test fixtures, resources, JSP/taglibs, reflective class strings и generated output;
- Spring artifacts во всех compile/runtime/test dependency trees и nested transitive edges, включая Spring LDAP/security artifacts; Maven parent/BOM, plugins, AspectJ weaving config после полного scan consumers, runtime packaging, WAR/containers и test launchers. Искать все groupId prefix `org.springframework` и artifact families, а не только один конкретный groupId;
- `META-INF/spring.factories`, `SpringBootServletInitializer`, `ApplicationContext`, component scanning, Spring annotations, `RestTemplate`, `SpringRunner`, `SpringBootTest`, `@Transactional` и Spring test utilities;
- оставшихся зависимостей на `SecurityContextHolder`/thread-local identity, кроме тестов, специально доказывающих её отсутствие.

Публичные config aliases вроде `spring.datasource.*` допустимы только в документированном parser/migration layer и тестах конфигурации; они не допускают зависимости от Spring jar. Исторические class names в Liquibase migration metadata — допустимое persistence compatibility исключение, зафиксированное и проверяемое без Spring runtime.
