# Архитектура транскодирования, стриминг и кэширование

Детальный анализ реализации аудиостриминга, конвейеров вызова внешних утилит, обработки HTTP Range-запросов и систем кэширования транскодированных потоков в **Airsonic Advanced** и **Navidrome**.

---

## 1. Концепция и архитектура транскодирования

Транскодирование (преобразование аудиокодека, битрейта, частоты дискретизации или разрядности на лету) необходимо при нехватке пропускной способности мобильной сети, воспроизведении на клиентах с ограниченным набором поддерживаемых кодеков (браузеры без поддержки FLAC/Opus) или при аппаратных ограничениях плееров.

### 1.1. Airsonic Advanced: Динамический конструктор командных строк из БД

Airsonic реализует историческую концепцию максимальной гибкости Subsonic:
- Все правила транскодирования хранятся в таблице базы данных `transcoding2` (модель `Transcoding.java`, DAO `TranscodingDao.java`).
- Правила транскодирования настраиваются администратором через интерфейс или API (`TranscodingSettingsController.kt`).
- Команда представляет собой шаблонную строку, в которой движок выполняет текстовую подстановку переменных (`generateTranscodingSubstitutionMap` в `TranscodingService.java`):

```text
ffmpeg -i %s -vn -b:a %bk -v 0 -f mp3 -
```

#### Таблица переменных подстановки Airsonic:
- `%s` — физический путь к исходному файлу на диске.
- `%b` — максимальный битрейт аудио (в кбит/с), запрошенный клиентом или ограниченный профилем пользователя.
- `%t`, `%a`, `%l` — название трека (title), имя артиста (artist), альбом (album).
- `%o` — смещение по времени в секундах (`timeOffset`).
- `%d` — длительность трека (`duration`).
- `%w`, `%h` — ширина и высота видеокадра (для видео).
- `%v`, `%r` — средний битрейт видео и аудио.
- `%i` — индекс выбранной аудиодорожки.
- `%j`, `%n` — индекс и имя HLS-сегмента.

#### Особенности и недостатки реализации Airsonic:
1. **Поддержка любых внешних бинарников и конвейеров (Pipes):** Администратор может использовать не только `ffmpeg`, но и связки утилит: `flac -c -d %s | lame -b %b -`, `opusdec`, `sox`.
2. **Безопасность (Command Injection):** Передача неэкранированных названий треков через подстановку `%t` или имен файлов с пробелами и спецсимволами (`"`, `'`, `$`, `;`) исторически создавала уязвимости инъекции команд ОС. В текущем коде форка подстановка разбивается на токены через `StringUtil.split` и передается массивом в `ProcessBuilder`, что нивелирует риск шелл-инъекций.
3. **Отсутствие гранулярного контроля за потоками:** Airsonic полагается на флаг `-vn` (отключить видео), однако в ряде сложных контейнеров с несколькими аудиопотоками ffmpeg может выбрать не тот поток без явного маппинга.

### 1.2. Navidrome: Встроенный монолитный конвейер FFmpeg

Navidrome принципиально отказался от хранения shell-строк в базе данных. Вызов FFmpeg жестко закодирован в модуле `core/ffmpeg/ffmpeg.go` и отлажен до байта:

```text
ffmpeg [-ss <offset>] -i <filePath> -map 0:a:0 -map_metadata 0 -map_metadata 0:s:a:0 \
       [-c:a <codec>] [-b:a <bitrate>k] [-ar <samplerate>] [-ac <channels>] \
       [-sample_fmt <fmt>] -v 0 -f <output_format> -
```

#### Инженерные преимущества пайплайна Navidrome:
1. **Входное позиционирование (`-ss <offset>` ПЕРЕД `-i`):**
   - Передача `-ss` перед входным файлом включает режим **Fast Input Seeking**. Демуксер ffmpeg прыгает прямо к ключевому фрейму по заголовкам файла без линейного декодирования предыдущих минут трека.
   - Задержка начала воспроизведения при перемотке сокращается с 2–5 секунд до **10–30 миллисекунд**.
2. **Защита от транскодирования обложек (`-map 0:a:0`):**
   - Флаг жестко предписывает брать *только первый аудиопоток*. Если файл содержит встроенный фронтальный арт (`0:v:0`), ffmpeg не будет тратить ресурсы CPU на безуспешные попытки сжать изображение как видеопоток.
3. **Двухуровневое копирование метаданных:**
   - `-map_metadata 0`: сохранение тегов контейнера (ID3v2, Vorbis Comments).
   - `-map_metadata 0:s:a:0`: перенос тегов конкретного аудиопотока (актуально для OGG/Opus).
4. **Безопасное управление сэмплами (`-sample_fmt`):**
   - Флаг передается **исключительно** при транскодировании во FLAC (`s16` или `s32`). Для lossy-форматов (MP3, AAC, Opus) этот параметр блокируется, так как LAME и libopus сами выбирают формат float32, а попытка форсировать целочисленный сэмпл приводила к аварийному завершению ffmpeg.
5. **Динамический патчинг заголовков FLAC (`flac_streaminfo.go`):**
   - При стриминге FLAC в pipe (`stdout`) ffmpeg не знает суммарного размера и длительности, поэтому выставляет в блоке `STREAMINFO` нулевые сэмплы (`total_samples = 0`).
   - Из-за этого многие мобильные плееры блокируют ползунок перемотки.
   - Navidrome перехватывает первые 26 байт потока на лету, рассчитывает $\text{total\_samples} = \text{duration} \times \text{sample\_rate}$ и бинарно переписывает 36 бит заголовка прямо в оперативной памяти до отправки в сокет.

## 2. Реализация стриминга и HTTP Range-запросов

| Характеристика | Airsonic Advanced | Navidrome |
|---|---|---|
| **Отдача оригинального файла (RAW)** | Чтение потока через `MediaStreamService.kt` | Использование стандартного `http.ServeContent` |
| **Поддержка HTTP 206 Partial Content** | **Да** (кастомный парсинг заголовков `Range: bytes=X-Y` в `StreamRestController.kt`) | **Да** (нативная поддержка Range и ETag в ядре Go `net/http`) |
| **Многодиапазонные запросы (Multipart Ranges)** | **Да** (`multipart/byteranges` с границами) | Ограничивается стандартным первым диапазоном |
| **Передача транскодированного потока** | Потоковая передача чанками (`Transfer-Encoding: chunked`) через `TranscodeInputStream.kt` | Буферизованная отдача с поддержкой сохранения в кэш |
| **Управление переполнением буфера процесса** | Фоновый поток вычитывает STDOUT/STDERR дочернего процесса | Ограниченный буфер вывода ошибок (4 КБ кольцевой буфер `limitedWriter`) |

## 3. Подсистема кэширования транскодированного потока (Transcoding Cache)

Это одно из ключевых архитектурных преимуществ Navidrome перед семейством Airsonic.

```mermaid
flowchart TD
    subgraph Airsonic["Airsonic: Прямой стриминг без кэша"]
        C1["Запрос трека (формат MP3, 192k)"] --> P1["Старт ProcessBuilder (FFmpeg)"]
        P1 --> ST1["STDOUT пайп в HTTP Response"]
        C2["Повторный запрос того же трека"] --> P2["Старт НОВОГО ProcessBuilder (FFmpeg)"]
        P2 --> ST2["STDOUT пайп в HTTP Response (CPU x2)"]
    end

    subgraph Navidrome["Navidrome: Полноценный дисковый TranscodingCache"]
        NC1["Запрос трека (формат Opus, 128k)"] --> LK["Проверка TranscodingCache (LRU)"]
        LK -->|Промах (Cache Miss)| NF["Запуск FFmpeg в фоновый кэш-файл"]
        NF --> WS["Одновременная отдача клиенту (TeeReader)"]
        WS --> SV["Файл сохранен в кэше"]
        NC2["Повторный запрос трека"] --> LK2["Проверка TranscodingCache"]
        LK2 -->|Попадание (Cache Hit)| SF["Мгновенная отдача файла с диска (0% CPU, HTTP 206 Range)"]
    end
```

### 3.1. Airsonic Advanced: Отсутствие кэша аудиопотоков
- В Airsonic транскодированный аудиопоток генерируется на лету и сразу транслируется в HTTP-сокет клиента.
- **Проблема:** Если один пользователь слушает альбом на повторе или несколько клиентов в семье одновременно включили один и тот же трек в транскодированном качестве, сервер будет запускать независимый процесс `ffmpeg` для **каждого** воспроизведения. Это создает огромную нагрузку на CPU сервера.

### 3.2. Navidrome: Встроенный LRU-кэш транскодирования
- Модуль `core/stream/media_streamer.go` инициирует `TranscodingCache` (`cache.NewFileCache`).
- Настройки:
  - Размер кэша: `conf.Server.TranscodingCacheSize` (по умолчанию: `100MB`, рекомендуется от `1GB` до `10GB`).
  - Расположение: папка `transcoding/` внутри директории данных.
- **Принцип работы:**
  1. При первом обращении результат работы `ffmpeg` через `io.TeeReader` одновременно транслируется в HTTP-ответ клиенту и сохраняется во временный кэш-файл с уникальным ключом `Hash(TrackID + Format + Bitrate + TargetSR)`.
  2. При любых повторных запросах того же трека (перемотка, повтор, запрос другим клиентом) Navidrome вообще **не запускает FFmpeg**, а отдает готовый файл с диска через `http.ServeFile`.
  3. Кэшированный файл моментально поддерживает полноценный HTTP Range (произвольная мгновенная перемотка без перезапуска процесса кодирования).
  4. При превышении размера кэша старые записи автоматически вытесняются по алгоритму LRU (Least Recently Used).
